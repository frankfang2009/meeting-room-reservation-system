# 会议室预约系统帮助文档内容标准

> 适用范围：`content/` 下的帮助中心文章。界面结构与构建规则见 `README.md`。

## 1. 文档目标

帮助文章不是功能介绍，也不是把《使用指南》拆成短段落。每篇文章必须帮助一类明确用户，在一个明确状态下安全完成任务或作出判断。

用户读完后应能回答：

1. 这件事是否适用于我的角色和当前预约状态；
2. 我现在应该从哪个页面开始、按什么顺序操作；
3. 怎样确认操作已经真正完成；
4. 操作会改变什么，不会改变什么；
5. 看到其他结果时如何处理，什么时候应停止并求助。

普通员工的日常自助是第一优先级。部署、用户、备份、恢复、升级等管理员内容必须使用更严格的风险写法。

## 2. 事实来源

帮助文档描述的是**当前正式版本实际运行产生的效果**，不是 Contract 的转述。文章中的事实按以下顺序核对：

1. **真实运行结果**：在当前正式版本中，用明确的角色、数据状态、平台和操作步骤复现用户实际看到的结果；
2. **完整代码调用链**：从前端入口和状态处理，沿 API、后端业务函数继续核对到数据库约束、定时任务或平台脚本；
3. **可复跑测试证据**：后端、前端、跨层或真实浏览器测试能够重现同一场景，而不是只检查某段源码文字存在；
4. **Contract 与使用指南**：用于理解设计意图、发现遗漏或实现偏差，不能在缺少运行与代码证据时单独证明文章事实；
5. 帮助中心其他文章只可用于避免重复，不可作为事实真值。

代码静态阅读也不是终点：权限、配置、当前时间、预约状态、平台和数据迁移都可能改变运行结果。复核时至少记录：

```yaml
verified_version: V2.5.0
verified_at: 2026-08-20
verified_scenario: employee / 未开始预约 / 时段冲突
source_code: [前端文件#函数, 后端文件#函数]
source_tests: [测试文件#测试名称]
```

不固定代码行号；使用文件、函数、API 或测试名称，避免普通重构造成无意义漂移。证据可以集中记录在内容证据索引中，不向最终用户展示内部源码路径。

发布状态、Windows/macOS 分发边界和版本支持范围必须另外核对发布清单，不能从产品功能是否存在反推。

运行结果、代码与 Contract 不一致时，不得自动选择其中一方并继续写作：先记录真实结果和调用链，再判断它是产品缺陷还是已接受行为；修复代码或更新产品决策后，才能发布对应文章。明显的 Bug 不得仅因为“现在就是这样运行”就被包装成正式规则。

出现以下情况时不得凭印象补写：

- UI 原文、限制数字或保留期限无法在当前来源中找到；
- 员工和管理员的结果不同，但来源没有说明；
- 涉及恢复、升级、数据删除、权限或隐私后果；
- 来源之间互相冲突。

此时在审计中标记“待核对”，确认后再发布。

## 3. 四种文章类型

### A. 操作型

适用于创建、修改、取消、交接、设置等有明确完成状态的任务。

推荐结构：

1. 一句话答案；
2. “开始前确认”：角色、对象和状态限制；
3. 编号步骤：使用页面与按钮原文；
4. “完成的标志”：用户可见的结果；
5. “操作后会发生什么”：归属、时段、通知、统计或历史的变化；
6. “如果没有按预期发生”：最多四个高概率分支；
7. 相关文章。

步骤只写一个成功路径。例外不得夹在步骤中打断主线。

### B. 规则解释型

适用于“为什么”“能不能”“谁能看到”“数据在哪里”等判断问题。

推荐结构：

1. 直接结论，通常不超过两句话；
2. 适用范围；
3. 规则及其对用户的实际影响；
4. 重要例外或不会发生的事情；
5. 用户可以采取的动作。

不要用后台实现细节代替用户结论。只有当实现机制能够证明隐私、安全或一致性边界时才解释，并同时翻译成用户影响。

### C. 故障排查型

适用于打不开、离线、保存失败、时间异常、无可用房间等症状。

推荐结构：

1. “先保护当前内容”：是否保持标签页、是否避免刷新或重复提交；
2. 按用户实际看到的提示语或状态分支；
3. 每个分支只给安全、可逆、由当前角色有权执行的检查；
4. 每一步写明恢复标志；
5. “停止并求助”：何时不应继续尝试；
6. “提供这些信息”：时间、页面、提示原文、请求编号等非敏感证据。

不得把“换浏览器”“重启服务器”“重新安装”当作未经判断的通用答案。不得要求普通员工导出数据库、日志、备份或发送含当事人、案号、凭据的截图。

### D. 管理员高风险型

适用于首次部署、用户权限、备份、恢复、升级、删除等可能影响多人或数据的操作。

推荐结构：

1. 影响范围与执行角色；
2. 操作前检查，包括必要的备份或当前状态；
3. 分阶段步骤，每阶段都有检查点；
4. 完成后的独立验证，不能只相信成功提示；
5. 不会发生或不应发生的结果；
6. 停止条件、回退边界和维护人员升级路径。

高风险文章不得把候选包、未签名制品或尚未完成的验收写成可正式分发结论。

## 4. 写作规则

- 标题写成用户会搜索的问题；清单型管理员文章可以使用明确任务名称。
- `summary` 是分类列表中的人工摘要：用 24–50 个字符的一句话说明读者能从本文解决什么问题，不截取正文，不重复标题，不使用 Markdown、Wiki Link 或省略号。
- 首屏先回答问题，不用欢迎语、背景故事或功能宣传开场。
- 一个段落只解决一个判断；长规则优先使用短列表或两到三列的小表格。
- 「页面」「按钮」「提示语」必须使用真实界面原文；引用完整提示时不得自行改写。
- “本人”明确指预约当前所有人；“当事人”不得写成预约员工。
- 明确区分“临近提醒”“预约变更通知”“工作交接请求”“管理员指派结果通知”。
- 明确区分“已结束”和独立完成状态：系统没有单独的“已完成”预约状态。
- 解释自动行为时，同时写明触发条件和用户是否需要操作。
- 不承诺跨标签页、跨浏览器或跨设备保留，除非当前产品契约明确支持。
- 不用“绝对安全”“永远不会出错”“已经发送”等无法由产品证明的表达。
- 示例使用“张女士”“李静”“笔录室 1”等合成信息，不写真实单位、人员、案号、地址或凭据。

## 5. 重复内容与链接

两篇文章可以讨论同一功能，但必须服务不同意图：

- “五分钟创建第一场预约”负责新用户第一次成功，只保留最短路径；
- “如何创建预约？”负责字段、限制和异常参考；
- 共同事实只在一篇展开，另一篇用 `related` 关联，避免两份长篇规则同步漂移。

相关文章链接用于承接下一步，不用于补齐当前文章缺失的必要步骤。读者不打开链接，也应能完成标题承诺的任务。

正文中需要在具体语境跳到另一篇文章时，使用显式 Wiki Link：

```markdown
[[bk-conflict]]
[[bk-conflict|时段被占了怎么办]]
```

- 目标使用稳定文章 ID，不使用可能改名的标题；
- `[[id]]` 自动显示目标文章标题，`[[id|显示文字]]` 用于贴合当前句子；
- 只链接能承接当前判断或下一步的关键词，不自动把正文中所有标签词变成链接；
- `tags` 负责搜索，`related` 负责文末推荐，Wiki Link 负责正文上下文跳转；
- 行内代码中的 Wiki Link 只作为示例展示，不解析；
- 目标不存在、ID 格式错误或显示文字为空时，构建必须失败。

## 6. 文章质量评分（16 分）

每项 0–2 分：0 为缺失或错误，1 为部分满足，2 为完整满足。

| 维度 | 2 分标准 |
| --- | --- |
| 用户与场景 | 明确角色、对象和适用状态 |
| 结论与可扫描性 | 首屏直接回答，结构能快速定位 |
| 事实准确性 | UI、数字、权限、版本与当前真值一致 |
| 任务完成度 | 给出可执行路径和用户可见的完成标志 |
| 后果与边界 | 说明会改变、不会改变及自动发生的结果 |
| 异常处理 | 覆盖高概率分支，并保护草稿或现场 |
| 安全与隐私 | 动作可逆且不诱导泄露、越权或危险操作 |
| 来源与维护 | 可指出事实来源、适用版本和复核日期 |

发布门槛：

- 14–16：可以发布；
- 11–13：修改后复核；
- 0–10：重写；
- 事实准确性、任务完成度、安全与隐私、来源与维护任一项为 0：无论总分多少都不得发布。

## 7. 审校清单

发布或重建前逐篇确认：

- [ ] 标题与文章实际回答的是同一个问题；
- [ ] `summary` 是 24–50 个字符的独立摘要，能帮助读者判断是否需要打开文章；
- [ ] 普通员工不会被引导进入管理员入口；
- [ ] 预约状态和所有权变化前后一致；
- [ ] UI 原文、数字、时间和保留期限有当前来源；
- [ ] 主路径有完成标志，异常路径有停止条件；
- [ ] 不包含真实人员、案号、地址、凭据、日志或客户截图；
- [ ] `related` 不形成死链，也不承担当前文章的必要步骤；
- [ ] `updated` 是最后一次事实复核日期，不只是文字编辑日期。
