# V2.2.1 macOS 自托管版与 DMG 分发方案

> 状态：已实现——macOS 自托管便携包、DMG、版本检查与 macOS CI 验收车道均随 V2.2.1 落地；
> 本文件保留为原始方案与决策记录，实现细节以代码和各契约文档为准
>
> 基线：V2.2.0（产品代际 2，数据库 schema v2，标签 `v2.2.0`）
>
> 目标版本：V2.2.1——V2.2.0 的 macOS 平台交付，不是新的功能主题
>
> 适用范围：当前 V2 仓库；不涉及 V1 数据、目录或迁移，不改变 Windows 版任何行为

## 1. 决策摘要

V2.2.1 是**平台交付版本**：业务功能与 V2.2.0 完全一致，交付目标是**让 GitHub 上的 macOS 用户可以下载 DMG、拖出、双击运行一个稳定可用的自托管 V2 实例，并在新版本发布后于系统状态页看到受控的更新提示。**

版本语义必须保持三条不变：

- `v2.2.0` 标签已冻结在既有提交，其 Windows 交付物 SHA 已公布核对；Mac 交付所需的新代码（启动器、打包脚本、版本检查模块）必须挂在新的版本号下，禁止两种源码状态共用同一版本号，维护“版本 ↔ 提交 ↔ SHA”证据链；
- Mac 交付物不建立自己的版本序列：它的版本号永远等于所包装的主线版本，V2.2.1 是第一个包含 macOS 交付的主线版本；今后每个主线版本（V2.3.0 起）在 Windows 交付物之外同步产出同版本号的 macOS 交付物；
- 本版本不占用功能主题位：按节奏规则修订为 `V2.2.x = 缺陷修复 + 平台交付扩展`；`V2.3.0` 继续保留给边界清楚的功能主题（如办理状态闭环）。

本版本包含三条相互独立、最终共同过发布门禁的工作流：

1. **macOS 冻结运行时与便携包**
   - 同一份 `v2app` 核心、`service.py` 进程模型与前端产物，打包进 arm64 冻结 Python 运行时；
   - 便携目录布局与 Windows 交付物同构（`app/ + runtime/ + data|backups|logs`），不改核心代码即可运行；
   - DMG 只是便携包的展示外壳；zip 是可复现的事实源。
2. **受控版本检查与更新提示**
   - 仅 macOS 版启用：服务端至多每 24 小时读一次 GitHub Release 的固定清单；
   - 只解析版本号并在管理员系统状态页显示“有新版本”与发布页链接；
   - 不自动下载、不自动安装、不发送任何本机数据；Windows 版继续维持“在线/自动升级”排除。
3. **macOS CI 验收与正式分发**
   - GitHub 的 macOS runner 即真实 Mac：PR/main 自动完成构建、挂载 DMG、真实首启、预约、大屏、备份冒烟；
   - 稳定版 DMG 通过 GitHub Release 正式分发，发布说明附 SHA-256；
   - Windows 双交付物门禁（T2 实机 + Authenticode）不变；本版本照常产出 V2.2.1 的 Windows 候选构建与升级验收腿（版本号机械同步，见 §13）。

V2.2.1 **不修改数据库 schema v2**，不新增业务表和业务字段；版本检查状态使用 `data/` 下的 JSON sidecar，不进数据库。数据库、API、前端行为除系统状态页新增一行外均不变。

## 2. 为什么这样定位

- V2.0.0 以来全部版本停留在候选状态，唯一阻塞是 Windows 实机与签名门禁，且短期内无法落实；
- 团队唯一拥有的真机平台是 macOS：macOS 版是第一个能由我们亲自完成“真实设备验收”闭环的发布物；
- 仓库已按 Apache-2.0 公开，存在真实的“下载即用”需求；当前唯一参与途径是源码自建，门槛过高；
- 从产品视角看，Mac 交付没有增加任何业务功能——它是分发与平台适配工作，因此用补丁版本号承载，不占用 V2.3.0 功能主题位；
- 代码基础已经就绪（本方案立项前已核实）：
  - `v2app` 核心 183 个 Python 文件零 win32 依赖；`backend/v2app/backup.py` 已有 darwin/linux 分支；
  - 每日备份调度在 `service.py` 进程内完成（`_launch_backup_catch_up`），不依赖 Windows 计划任务；
  - 身份体系对“无 install.json”有显式开发态兼容（`load_or_create_install_id`）；
  - `service.py` 用 pid 文件 + 回环控制请求管理启停，所有路径相对 `app/` 目录，天然可移植；
  - 开发工具链（`bootstrap-dev.sh`、`check.sh`）全 bash，测试套件可在 macOS 全量运行。

## 3. 产品目标与成功标准

### 3.1 产品目标

- 一名使用 Apple Silicon Mac 的 GitHub 用户，从 Release 页下载 DMG 后，在 5 分钟内完成：拖出文件夹 → 双击“启动” → 浏览器自动打开 → 完成首次设置 → 创建第一笔预约，全程不需要安装 Python、Node 或任何依赖；
- 管理员在日常使用中打开系统状态页，即可看到“当前版本 V2.2.1”以及（当主线发布新版本时）“有新版本 V2.3.0 可用 · 查看发布页”；
- 用户的全部业务数据（数据库、备份、日志、身份）保存在应用文件夹内的 `data/`、`backups/`、`logs/`，删除应用文件夹即彻底卸载，无系统残留；
- 服务长期运行时，既有能力原样可用：共享日历、预约管理、数据中心、CSV 导出、公开大屏、每日自动备份。

### 3.2 可验收的成功标准

- DMG 在 macOS 13+ arm64 真机（含 CI runner）上可挂载、可拖出、双击启动并完成首次设置与预约创建；
- 直接从挂载卷（`/Volumes/` 下）双击启动时，得到明确的“请先拖出到应用程序或任意文件夹”提示并安全退出，不产生半初始化现场；
- 同一源代码提交的两次独立构建产出字节一致的 zip；DMG 由该 zip 内容生成并附 SHA-256（DMG 本身不承诺字节级可复现，见 §5.3）；
- 版本检查：本地伪造的清单服务器可驱动全部测试（新版本提示、同版本不提示、格式错误、超时、超体积、离线），任何失败都安静降级，不出现成功对勾，不影响业务功能；
- employee 会话在任何接口上都拿不到版本检查结果；未启用版本检查的构建（Windows、开发态）行为与 V2.2.0 完全一致；
- “停止”入口使用 `service.py --stop` 语义（pid + 回环控制），不按端口或进程名杀进程；
- 公开大屏、登录限速、会话时限、CSRF 等安全行为与 Windows 版同一份代码、同一套测试覆盖。

## 4. 部署形态与平台边界

### 4.1 macOS 自托管版定义

| 维度 | 决定 |
| --- | --- |
| 目标用户 | 从 GitHub Release 下载的个人自托管用户（单机为主） |
| 架构 | 仅 arm64（Apple Silicon）；x86_64/universal2 有真实需求再评估 |
| 系统下限 | macOS 13（Ventura）起，CI 在 macos-14/15 runner 验收 |
| 运行形态 | 前台服务：双击 `启动.command` 在终端运行，关闭窗口或 `停止.command` 停止；不做 launchd 开机自启 |
| 数据位置 | 便携式：`data/`、`backups/`、`logs/` 与 `app/`、`runtime/` 同级，均在应用文件夹内 |
| 网络姿态 | 首次设置前仅绑定 127.0.0.1；设置后绑定 0.0.0.0 供可信局域网访问；HTTP 明文风险与 Windows 版相同，文档引导“个人本机使用优先” |
| 升级方式 | 下载新 DMG → 停止服务 → 替换 `app/`、`runtime/` → 保留 `data/`、`backups/`、`logs/`；不提供自动化升级 |
| 签名 | 首版不签名不公证；文档说明右键打开/去除隔离属性两种首次运行方法；Developer ID + 公证是后续独立决策 |

### 4.2 与 Windows 版的关系

- 同一代码库、同一 schema、同一 API；差异只存在于交付物打包层与版本检查开关；
- Windows 双交付物（安装包、累计升级包）的构建、验收与正式外发门禁**原样保留**，本主题不触碰 `installer/` 现有行为；
- 不承诺 Windows ↔ macOS 跨平台数据库迁移支持；两平台各自只承诺同平台保留数据升级；
- 版本检查是 macOS 版专属能力（见 §7.4），Windows 版继续执行“不做在线或自动升级”的契约排除。

### 4.3 复用与新增的边界

复用（不改或近零改动）：`v2app` 全部业务代码、`service.py` 进程模型、`server.py` 绑定切换、`backup.py`、前端产物与构建链、依赖哈希锁方法论、SBOM/通知/来源证明生成器。

新增：macOS 运行时冻结脚本、便携包组装脚本、DMG 生成脚本、`启动.command`/`停止.command`、版本检查模块与系统状态页展示、macOS CI 车道、GitHub Release 发布流程。

## 5. 交付物与包结构

### 5.1 交付物清单

同一个稳定版本从同一源代码提交生成：

| 交付物 | 形态 | 用途 |
| --- | --- | --- |
| `会议室预约系统-V{版本}-macOS-arm64.zip` | 可复现 zip | 字节级事实源、校验对象、CI 验收入口 |
| `会议室预约系统-V{版本}-macOS-arm64.dmg` | UDZO DMG | 用户下载与拖出安装的正式形态 |
| `latest-macos.json` | 清单 | 版本检查的事实源，随 Release 附带 |
| `.sha256` / `.sbom.cdx.json` / `.runtime-provenance.json` / `.THIRD-PARTY-NOTICES.txt` | 伴生文件 | 与 Windows 交付物同规格 |

首个 macOS 交付物对应主线版本 V2.2.1；此后每个主线版本的 Release 同步附带同版本号 macOS 交付物。

### 5.2 便携包目录结构

```
会议室预约系统V2-macOS/
├── 启动.command          # Finder 双击入口：卷守卫 → 前台启动 → 自动开浏览器
├── 停止.command           # 调 service.py --stop（pid + 回环控制）
├── 使用说明.txt           # 首次运行（Gatekeeper）、升级、备份位置说明
├── app/                  # service.py + v2app + static/（与 Windows 生产布局同构）
├── runtime/              # 冻结 Python 3.13.x arm64 + 依赖
├── data/                 # 首启后生成：数据库、secret、身份、update-check.json
├── backups/              # 首启后生成：每日备份
└── logs/                 # 首启后生成：轮转日志
```

`启动.command` 职责：检测自身路径位于 `/Volumes/` 时提示拖出并退出；设置 `MEETING_ROOM_OPEN_BROWSER=1`；以 `runtime` 内解释器前台运行 `app/service.py`；终端窗口标题显示产品与版本。

### 5.3 可复现性口径

- zip 是可复现事实源：两次独立构建字节一致，验收方式与 Windows 交付物相同；
- DMG 用 `hdiutil` 从已验证的 zip 展开内容生成（UDZO、固定卷名）；hdiutil 的元数据不保证跨构建字节一致，因此**不把 DMG 纳入双构建字节一致门禁**，改为：DMG 由通过校验的 zip 内容生成 + 发布 SHA-256 + CI 从 DMG 反向展开校验关键文件哈希；
- 所有伴生文件（SBOM、来源证明、通知）的生成器从现有 Windows 管线复用，仅替换运行时来源记录。

## 6. 冻结运行时与依赖

- **解释器**：Python 3.13.x，arm64，优先采用 python-build-standalone 固定版本 tarball（SHA-256 锁定，来源记录进 runtime-provenance）；备选 python.org macOS 安装包提取。此项是 §13 开放决策之一；
- **依赖锁**：新增 `requirements-macos-arm64.lock`，`--require-hashes` 固定；Flask/waitress 为纯 Python wheel，锁复杂度远低于 Windows embed 发行版；
- **前端**：Vite 生产构建产物随包分发，用户不需要 Node；构建管线复用现有 frontend 供应链脚本；
- 运行时与依赖不得携带：测试数据、`node_modules`、源码映射、开发工具、V1 任何内容。

## 7. 版本检查与更新提示

### 7.1 行为定义

- 服务启动时与之后每 24 小时至多执行一次检查；管理员在系统状态页可手动触发一次立即检查（限频）；
- 检查成功且远端版本大于当前版本时，系统状态页“版本”行显示“有新版本 V{x.y.z} 可用 · 查看发布页”；相同或更低版本不显示；
- “查看发布页”链接由**服务端**用内置仓库常量 + 清单中的 tag 构造（形如 `https://github.com/frankfang2009/meeting-room-reservation-system/releases/tag/{tag}`），**不使用清单自带的任何 URL**，防止清单被篡改后注入钓鱼链接；
- 仅管理员可见；员工导航、接口与页面不出现任何更新信息；
- 任何失败（网络不通、超时、格式错误）只导致“不显示”，手动检查时显示中性的“暂时无法检查更新”；绝不使用成功对勾语义，绝不阻塞业务。

### 7.2 清单 `latest-macos.json`

通过固定 URL 获取（GitHub 的 latest-release 资产重定向，不经过 API、不受 API 限速影响）：

```
https://github.com/frankfang2009/meeting-room-reservation-system/releases/latest/download/latest-macos.json
```

字段为受验证的严格 schema：`product`（固定值校验）、`channel`（固定 `macos-selfhost`）、`version`（语义化版本）、`tag`。多余字段忽略，缺失字段视为格式错误。

### 7.3 实现边界

- 仅 HTTPS、仅固定主机、10 秒超时、响应上限 64 KiB；
- 只解析版本号与 tag，不下载、不执行、不落盘任何程序内容；
- 检查状态（上次检查时间、上次结果）保存在 `data/update-check.json` sidecar，不进数据库，schema 保持 v2；
- 请求不携带任何本机信息：无单位名、无用户数、无 install_id、无统计标识；隐私表述写入文档（“该请求向 github.com 发送的内容与直接在浏览器打开该网址相同”）；
- 结果记入服务日志一行，不进业务安全审计；
- 测试全部通过本地伪造 HTTP 服务器驱动，CI 与单测不访问真实 GitHub。

### 7.4 启用开关

- 打包器在 macOS 便携包的 `install.json` 写入 `edition: "macos-selfhost"`；服务端仅当 edition 匹配时启用版本检查；
- 开发态（无 install.json）与 Windows 安装（edition 为 windows）默认关闭；
- 提供仅测试用的环境变量覆盖清单 URL；生产构建不受影响。

## 8. 安全与隐私边界

- 除 §7 的固定清单 GET 请求外，macOS 版不新增任何外网访问；看板、图表、大屏继续零外网请求；
- HTTP 明文姿态与 Windows 版一致：局域网内凭据与业务信息明文传输，文档明确提示并引导单机使用或可信网络；
- 未签名 DMG 的 Gatekeeper 处置如实文档化：右键“打开”或 `xattr -dr com.apple.quarantine`，不以任何方式教唆关闭系统安全功能；
- `data/`、`backups/`、`logs/` 在 macOS 上使用用户级权限（0755/0600 语义沿用现有代码），不引入需要管理员授权的权限模型；
- 公开仓库、CI、DMG 内不得携带客户数据库、真实个人信息、日志或密钥——沿用现有红线。

## 9. CI 与验收分层

沿用现有分层思想，新增 macOS 车道（证据编号在记入 RELEASE-CHECKLIST 时正式分配，暂记 E47–E51）：

| 层 | 内容 | 触发 |
| --- | --- | --- |
| E47 mac 测试车道 | macos arm64 runner 上运行全量测试套件（对齐 `check.sh` 能力子集 + macOS 特有单测） | 每个 PR / main |
| E48 mac 候选构建 | 两次独立构建 zip 字节一致；生成 DMG、SHA-256、SBOM、通知、来源证明 | 版本标签 `v2.*` |
| E49 mac 真实验收 | runner 上：挂载 DMG → 从 `/Volumes/` 直接启动得到拖出提示 → 拖出后启动 → `/healthz` → 首次设置 → 建预约 → 大屏脱敏 → 等待首份备份落盘且无 WAL 伴随文件 → `停止.command` 干净退出 | E48 之后同一 run |
| E50 版本检查验收 | 本地清单服务器驱动：新版本提示、同版本静默、畸形 JSON、超体积、超时、离线、员工 403、非 mac 构建零行为差异 | E47 内含 |
| E51 发布演练 | 从 tag run 产物创建 Draft Release：附 DMG/zip/清单/SHA，校验 `releases/latest/download/latest-macos.json` 重定向可达 | 手动，首次发布前一次 |

CI 策略约束沿用：`ci.yml` 不制作不上传安装物；macOS 候选产物只从 main 上的版本标签构建。

## 10. 发布与分发流程

1. 合并 V2.2.1 → main → 打 `v2.2.1` 标签 → E48/E49 全绿；
2. 从 tag run 下载产物，本地复核 SHA-256 与 dry-run 一致（流程与 v2.2.0 打标核对相同）；
3. 创建 GitHub Release：附 macOS zip、DMG、`latest-macos.json`、`.sha256`；发布说明含 SHA-256 与“未签名首次打开”说明；
4. 发布后用 E51 方法验证 latest 重定向；
5. Windows 双交付物是否随 Release 附带，仍由其自身门禁决定，本流程不改变。

**规则修订**：RELEASE-CHECKLIST 现行“公开仓库不得自动发布 V2 候选”修订为按交付物分类——macOS 自托管版以 GitHub Release 为正式分发渠道，其“稳定”门禁为 E47–E51 全绿 + 团队真机抽验 + SHA 公布；Windows 安装包/升级包在 T2 实机 + Authenticode 完成前继续禁止外发（`formal_external_release_allowed` 细化为按交付物适用）。

## 11. 开发拆分与顺序

### 阶段 A：运行时与便携包（最大头）

- 选定并锁定 arm64 Python 运行时来源与哈希；建立 `requirements-macos-arm64.lock`；
- 实现便携包组装脚本（zip 事实源）与 `启动.command`/`停止.command`（含 `/Volumes` 守卫）；
- 本机（Apple Silicon）手工全流程跑通：解包 → 启动 → 首次设置 → 预约 → 备份 → 停止。

### 阶段 B：版本检查

- 后端模块（限频、超时、体积上限、严格 schema、服务端构造发布页 URL）+ `data/update-check.json` sidecar；
- 系统状态页“版本”行扩展：徽标 + 链接，仅管理员；
- 全部用本地伪造清单服务器完成单测与契约测试。

### 阶段 C：DMG 与候选构建

- `hdiutil` DMG 生成脚本（固定卷名、拖出布局、说明文件）+ 反向展开校验；
- `release-candidate.yml` 增加 macos 候选车道（双构建字节一致门禁只针对 zip）。

### 阶段 D：CI 验收

- E47 测试车道与 E49 真实验收脚本（runner 即真 Mac）；
- E50 验收纳入 E47。

### 阶段 E：契约、文档与发布

- PRODUCT-CONTRACT 增补 macOS 自托管版章节；RELEASE-CHECKLIST 按交付物分类修订外发规则并定义 mac 稳定门禁；
- README（中英）快速上手、升级与 Gatekeeper 说明；
- CHANGELOG 记录 V2.2.1（业务功能与 V2.2.0 一致，新增 macOS 平台交付与更新提示），VERSION 提升至 2.2.1（最后一个提交统一处理）；
- Windows 升级验收腿（`v2-windows-upgrade-acceptance` 等）版本号同步至 v2.2.1；
- E51 发布演练 → 团队真机抽验 → 正式 Release。

各阶段在 `codex/v2.2.1-macos-selfhost` 分支进行，按仓库惯例 PR 合并后删除分支与 worktree。

## 12. 测试与验收矩阵

- **运行时与打包**：zip 双构建字节一致；DMG 反向展开关键文件哈希与 zip 一致；包内无测试数据/开发工具/V1 内容；`启动.command` 在 `/Volumes/` 下正确拒绝、拖出后正常启动；
- **功能冒烟（真 runner）**：`/healthz` 首启仅回环信息；首次设置事务完整；创建/修改/取消预约；员工/管理员权限行为；数据中心与 CSV；公开大屏脱敏与隐藏房间；登录限速与会话过期；
- **备份**：首启后备份 catch-up 产生独立非 WAL 文件，无 `-wal/-shm/-journal/.part-*` 残留；`logs/` 轮转；
- **版本检查**：§3.2 全部条目 + 清单 `product/channel` 不匹配、版本号非语义化、URL 构造固定主机、24 小时限频、手动检查限频、sidecar 损坏时安静重来；
- **权限**：employee 与未登录对版本检查接口稳定 401/403；Windows/开发构建零差异（行为快照测试）；
- **视觉**：系统状态页新增行在 1024×720 与 1440×900 下不破版；徽标不使用纯颜色语义；
- **安全**：除固定清单 GET 外无外网请求（断网冒烟全功能可用）；DMG 与包内文件无客户数据。

## 13. 开放决策与风险

1. **运行时来源**：python-build-standalone（推荐：哈希可锁、免安装提取）vs python.org 安装包提取——阶段 A 首项定案；
2. **macOS 版本矩阵**：CI 仅覆盖 runner 镜像（macos-14/15）；macOS 13 的实际覆盖依赖团队真机抽验补足；
3. **DMG 可复现性**：已按 §5.3 降级为“内容校验 + SHA 公布”，如后续找到确定性生成方案再升级；
4. **隔离属性摩擦**：未签名首启需右键打开，用户体验有损；接受并如实文档化，公证作为后续独立决策；
5. **支持负担**：公开发布二进制会带来环境多样性 issue；SUPPORT.md 已声明无担保，仍需心理预期；
6. **版本堆叠**：macOS 版加入后每个版本多一个交付物与一条验收车道，节奏规则（V2.2.x 只修复 + 平台交付）必须坚持；
7. **Windows 车道随动成本**：打 `v2.2.1` 标签会照常产出 Windows 候选构建，升级验收腿的版本号需机械同步（v2.1.0/v2.2.0 → v2.2.1 来源矩阵）——这是任何版本提升的固有成本，不是本方案的额外负担，但排期时要计入。

## 14. 明确不在 V2.2.1

- launchd 开机自启、后台守护或登录项；
- Developer ID 签名、公证、Sparkle 或任何自动更新框架；
- 一键下载并自动安装升级（“软件内更新”止步于提示 + 链接）；
- x86_64 / universal2 双架构；
- `.app` 束、菜单栏常驻、Dock 集成等原生壳形态；
- Windows 版版本检查或任何在线升级能力；
- Windows ↔ macOS 数据迁移承诺；
- 云端托管、跨公网访问、遥测统计（清单 GET 除外）；
- 手机端适配、AI 功能、V1 兼容；
- 任何业务功能主题（留给 V2.3.0）。

## 15. 开发启动前的最终确认项

本方案给出以下默认决定，若无异议即可按 §11 拆卡：

1. 版本号定为 **V2.2.1**，定位“V2.2.0 的 macOS 平台交付”，修订节奏规则为 `V2.2.x = 缺陷修复 + 平台交付扩展`；V2.3.0 主题位保留给功能主题；
2. 仅 arm64，系统下限 macOS 13，CI 覆盖 macos-14/15；
3. zip 为可复现事实源，DMG 只做内容校验 + SHA 公布，不进双构建字节门禁；
4. 便携目录布局，前台运行，无 launchd；
5. 版本检查仅 macOS 版启用（`install.json` edition 标记），每 24 小时至多一次，仅管理员可见；
6. 清单经 `releases/latest/download/latest-macos.json` 固定 URL 获取，服务端自行构造发布页链接；
7. 检查状态存 `data/update-check.json`，数据库 schema 保持 v2；
8. 首版不签名不公证，右键打开/去隔离如实写入文档；
9. GitHub Release 成为 macOS 版正式分发渠道，外发规则按交付物分类修订，Windows 门禁不变；
10. 阶段顺序 A→E，全部在 `codex/v2.2.1-macos-selfhost` 分支进行。
