# V2.2.0 服务数据中心与累计升级方案

> 状态：方案草案，待产品确认后拆分开发任务
>
> 基线：V2.1.0（产品代际 2，当前数据库 schema v2）
>
> 目标版本：V2.2.0
>
> 适用范围：当前 V2 仓库，不涉及 V1 数据、目录或迁移

## 1. 决策摘要

V2.2.0 采用一个清晰主题：**让每名员工能够查看并导出自己的服务数据，让管理员能够在个人视角与全单位 overall 视角之间切换；同时首次交付可验证、可回滚的 V2 离线累计升级包。**

本版本包含两条相互独立、最终共同过发布门禁的工作流：

1. **服务数据中心**
   - 所有已认证用户都能进入数据中心；
   - employee 只能查看和导出本人名下的服务信息；
   - admin 默认查看全单位 overall 面板，也可选择任一人员进入与该员工相同口径的个人面板；
   - 办件明细 CSV 的数据范围始终与当前已授权面板一致；
   - 固定口径、固定查询，不提供任意 SQL 或数据库浏览器；
   - 所有统计和导出均在本机 V2 服务端完成，不上传数据。
2. **V2 离线累计升级**
   - 新用户继续使用完整安装包；
   - 已安装 V2 的用户使用独立、完整、可跨过中间小版本的累计升级包；
   - 更新过程保护数据、配置、安装身份和运行状态，失败自动回滚；
   - 不提供在线下载、网页上传更新包或浏览器执行更新。

V2.2.0 原则上**不修改数据库 schema v2**。数据中心只读取现有预约、笔录室、用户、标签和审计字段；产品版本升级不等于数据库结构必须升级。这样可以把第一代生产更新器的风险优先收敛到“程序替换 + 数据保护”，而不是同时引入不必要的数据迁移。

## 2. 为什么选择这个功能

V2.1.0 已覆盖账号、权限、笔录室、预约、冲突控制、历史记录、备份恢复和局域网部署等基础能力。下一步最有价值的不是继续增加表单，而是把已经沉淀的数据变成员工和管理员各自可行动的信息：

- 员工可以回顾自己的服务安排、工作时长和忙碌分布，并直接导出本人明细；
- 日常需要向上汇报时，可以直接看到一段时间内的办件规模和变化；
- 需要核对具体业务时，可以导出结构稳定的办件明细；
- 日常汇总尽量在系统内完成，减少导出后再手工做透视表；
- 数据始终留在当前 Windows 机器和可信局域网边界内。

这也是一次适合验证后续升级模式的版本：功能对用户可感知，但业务数据结构可以保持不变，适合作为 V2 第一套累计升级链路的正式落地目标。

## 3. 产品目标与成功标准

### 3.1 产品目标

- 员工在 1 分钟内看清“这段时间我安排了多少服务、已经走过预约时间的有多少、主要集中在哪些日期、时段和业务标签”。
- 管理员在 1 分钟内回答“全单位服务量如何变化、笔录室与时段负荷集中在哪里、取消波动是否值得核查”，并可通过顶部人员选择器进入任一人的个人面板。
- 员工和管理员无需接触 SQLite 文件、表结构或 SQL，即可导出各自权限范围内、可由 Excel 直接打开的办件明细。
- 看板与 CSV 对同一筛选条件使用同一口径，避免“页面一个数、导出又是另一个数”。
- 从受支持的 V2 基线升级到 V2.2.0 时，不丢失账号、预约、设置、备份、日志、安装身份或未知现场数据文件。

### 3.2 可验收的成功标准

- employee 可以按日期、笔录室、本人适用标签和关键词筛选，但服务端始终把数据收窄到本人；CSV 另可筛选有效或已取消状态。
- admin 默认查看 overall 面板，可选择一名员工进入个人面板，并可随时回到 overall。
- admin 的 CSV 只导出当前视角：overall 导出全单位筛选结果，个人面板只导出所选人员结果。
- 在相同视角、日期、笔录室、标签和关键词下，看板有效预约指标与 CSV 的有效记录、取消辅助指标与 CSV 的已取消记录分别重新计算一致。
- employee 即使伪造 `overall`、`person` 或他人 `ownerId` 参数，也不能获得任何他人聚合或明细。
- CSV 可被 Windows Excel 正确识别中文、换行和日期文本，并阻止公式注入。
- V2.2.0 新装包与累计升级包来自同一源代码提交、同一版本和同一发布清单。
- 累计升级在成功、主动取消、负载损坏、磁盘不足、服务停止失败、健康检查失败和中断恢复等情形下均有明确结果；失败不会留下“程序已换、版本已写、数据却未完成”的半升级状态。
- 自动化通过不等于正式发布；真实 Windows 10/11 普通用户验收和签名门禁仍必须完成。

## 4. 用户与权限边界

### 4.1 角色

| 能力 | employee | admin |
| --- | --- | --- |
| 看到“数据中心”导航 | 是 | 是 |
| 查看本人数据看板 | 是 | 是 |
| 导出本人办件明细 CSV | 是 | 是 |
| 查看全单位 overall 面板 | 否 | 是 |
| 选择并查看其他人员面板 | 否 | 是 |
| 导出全单位或其他人员明细 | 否 | 是 |
| 查看任意数据库表或执行 SQL | 否 | 否 |
| 通过网页下载原始 SQLite 数据库 | 否 | 否 |

前端隐藏不构成权限控制。所有看板与导出接口都必须由 Flask 重新验证当前会话，并先解析服务端授权的数据视角，再构造查询：

- employee 的授权视角永远是 `self`，基础查询必须强制增加 `owner_user_id = current_user.id`；
- admin 可使用 `overall`，也可使用带明确 `ownerId` 的 `person`；
- employee 提交 `overall`、`person` 或他人 `ownerId` 时稳定拒绝，不允许静默扩权，也不泄露目标用户是否存在；
- CSV 与看板调用同一个视角解析器，不能出现“页面只看本人，导出接口却漏掉 owner 条件”；
- 不使用只读集成 token 代替已认证用户权限。

### 4.2 页面位置

新增所有已认证用户可见的独立导航项“数据中心”，不放入“系统状态”。

- “系统状态”继续承担数据库、服务、备份、端口和工作时间等低频运维信息，保持安静的运行账本；
- “数据中心”承担业务统计与导出，允许更高的信息密度；
- employee 进入后固定显示“我的数据”，页面中不出现人员选择器；
- admin 进入后默认显示“全单位概览”，页头提供“全单位 / 选择人员”视角切换；选择人员后，页面明确显示“正在查看：姓名 · 部门”，并使用与员工本人完全相同的个人指标；
- 已停用但仍有历史预约的人员可以由 admin 选择，并明确标注“已停用”；停用不应抹去历史统计；
- 切换视角必须清空不再适用的人员标签、游标和旧图表结果，导出区同步显示当前授权范围。

## 5. 数据看板方案

### 5.1 页面结构

页面按“视角 → 筛选 → 概览 → 趋势 → 诊断分布 → 导出”的顺序组织：

1. 顶部：标题、当前数据视角、口径说明、数据更新时间；
2. admin 视角选择器：全单位 overall 或某一人员；employee 不显示；
3. 全局筛选条：日期范围、笔录室、适用标签、关键词；
4. 概览：少量核心指标；
5. 趋势：所选范围内按周变化；
6. 诊断分布：根据个人视角或 overall 显示真正可行动的分布；
7. 办件明细导出：显示当前授权范围、筛选条件、预计行数和导出操作。

视觉继续使用 V2 的暖象牙白、石墨色和克制的陶土色。图表优先使用 React + 原生 SVG 实现，不依赖外部 CDN，不复制许可证不兼容的第三方模板。若以后引入图表库，必须本地打包、固定版本、纳入 SBOM 和离线构建验证。

### 5.2 默认筛选

- 默认日期：服务器本地日期所在自然月的第一天至当天；
- 可选日期跨度：单次最多 366 天；
- 笔录室：默认全部；
- 标签：默认全部；
- 关键词：默认空，匹配当事人、案号、事项和备注；
- 所有业务日期和时段按服务器本地时间解释，技术时间戳仍使用 UTC RFC3339。

标签继续遵守现有所有权规则：

- employee 的个人视角可使用全局标签和本人的个人标签；
- admin 的某一人员视角可使用全局标签和该人员的个人标签；
- admin overall 只能使用全局标签，因为不同员工的个人标签没有可安全汇总的共同语义；
- 视角改变时清空不再适用的个人标签筛选；
- 历史结果展示预约保存时的标签文案快照，不能用后来改名后的当前文案覆盖。

筛选改变后，页面必须以一次新的、完整的查询结果替换旧结果。旧筛选下的图表不得与新标题短暂混用；加载时保留框架和安静骨架。

看板不提供会让主指标失去语义的状态筛选。看板始终同时计算有效预约主指标和已取消辅助指标；若筛选为“只看已取消”，有效预约、已结束预约和预约时长会同时变成 0，不能帮助用户决策。状态筛选仅放在 CSV 导出区域，用于选择要导出的明细。

### 5.3 指标选择原则

首版指标只保留满足以下条件的内容：数字变化后，当前用户知道应当查看什么或调整什么；能够由现有 schema v2 稳定计算；不会把预约状态误说成办件结果。

因此不把指标简单堆成同一套六张卡，而是区分个人工作回顾和单位资源调度。每个视角保留 3 个主指标，其余作为诊断或防误读信息。

### 5.4 employee 与 admin 个人面板

employee 查看本人时、admin 选择某一人员时，使用完全相同的指标版本 `personal-service-v1`。

#### 主指标

| 显示名称 | 固定口径 | 为什么有价值 |
| --- | --- | --- |
| 有效预约 | 筛选范围内 `status=active` 的本人预约数 | 反映本人当前有效服务安排规模，是最直接的工作量入口 |
| 已结束预约 | 上述有效预约中，预约结束日期时间不晚于服务器当前本地时间的数量 | 帮助本人回顾已经走过预约时段的工作；只能称“已结束预约”，不能称“已完成办件” |
| 预约时长 | 筛选范围内有效预约的 `end-start` 分钟数之和 | 比单纯次数更能反映不同预约时长造成的工作量差异；不宣称实际办理时长 |

#### 诊断图表与辅助信息

- **按周工作量趋势**：同时展示有效预约数和预约时长，回答“哪几周更忙”；
- **标签分布**：按保存时标签快照展示本人服务类型构成，未标记单独列出；这比“常用标签”单值更能帮助整理工作；
- **时段分布**：把有效预约占用槽汇总为每周七天的上午/下午两段，帮助调整个人排期；详细半小时矩阵不在首屏展示；
- **变动提示**：显示筛选范围内已取消数量，但不把个人取消率作为主 KPI。当前数据无法区分取消原因，也不能把管理员代为取消直接归因到员工表现；
- **即将开始**不放入受任意历史筛选控制的 KPI 卡，继续由现有“我的预约/提醒”承担即时行动，避免看板与待办入口重复。

### 5.5 admin overall 面板

admin 的全单位视角使用指标版本 `overall-service-v1`，服务于资源调度与异常核查，不用于个人绩效考核。

#### 主指标

| 显示名称 | 固定口径 | 为什么有价值 |
| --- | --- | --- |
| 有效预约 | 筛选范围内全单位 `status=active` 的预约数 | 回答单位服务安排总规模 |
| 预约总时长 | 全单位有效预约的 `end-start` 分钟数之和 | 比次数更准确地反映笔录室与人员承载需求 |
| 已结束预约 | 全单位有效预约中，预约结束日期时间不晚于服务器当前本地时间的数量 | 反映已有多少安排走过预约时段，但不冒充办结量 |

#### 诊断图表与辅助信息

- **按周工作量趋势**：有效预约数与预约总时长，查看需求变化；
- **单一分析区**：使用“时段分布 / 笔录室 / 标签”三个页签，一次只显示一个维度，避免多块图表同时竞争注意力；
- **人员查看**：不再渲染全员工作负荷长列表；管理员通过顶部人员选择器进入个人面板，避免把员工并排比较；
- **笔录室**：各笔录室有效预约数与预约时长，支持管理者调整资源；不称“利用率”；
- **时段分布**：把全单位占用槽汇总为每周七天的上午/下午两段，为工作时间和笔录室安排提供依据；
- **标签**：只汇总单位统一管理的标签 1、2 与未使用全局标签的记录，不跨人员拼接个人标签含义；
- **取消波动**：显示已取消数量和取消率 `cancelled / (active + cancelled)`，作为需要核查的 guardrail；分母为 0 时显示“—”。取消率不能用于员工排名，因为系统没有取消原因与责任归属。

### 5.6 与现有“我的活动”的关系

V2.1.0 个人中心已有“我的活动”，但它使用累计完成、累计时长等另一套口径。V2.2.0 不能保留两套互相竞争的数据真值：

- 数据中心成为可筛选、可导出的个人分析主入口；
- 个人中心若保留“我的活动”，必须改为复用同一 reporting service 的安静摘要，并提供“查看完整数据面板”入口；
- 不再独立维护另一套 SQL、完成定义或常用标签统计；
- 现有 API `/api/v1/activity` 应复用共同查询层或在兼容期后退役，具体方式在 API 合同变更时确定。

### 5.7 明确不做的指标

- 不做绩效排名、个人分数、红黑榜或全员工作负荷列表；管理员只通过顶部选择器进入个人视角；
- 不做“笔录室利用率百分比”。现有数据库没有保存房间在历史日期是否启用、历史工作时间和临时不可用时段，缺少可靠分母；
- 不把 `active` 自动解释为“已完成”“已到场”或“实际办理”。V2.1.0 只有预约有效/已取消状态；
- 不统计“案件数”或“服务人数”。案号可能为空或不规范，同名当事人也不能稳定去重；
- 不展示平均办理时长。现有数据只有预约时长，没有实际开始、结束或办理耗时；
- 不推断案件受理、调查、决定或送达状态；预约成功不等于行政业务状态已经完成；
- 不以预约人姓名变化回写历史，继续使用预约创建时的 owner 快照语义。

## 6. 办件明细 CSV 方案

### 6.1 定位

操作名称固定为“导出办件明细 CSV”。CSV 用于核对和留存明细，不承担系统内已经能够完成的汇总统计。

导出范围必须绑定当前面板视角：

- employee 只能导出本人明细；
- admin 在 overall 面板导出全单位筛选结果；
- admin 在某一人员面板只导出该人员筛选结果；
- 切换视角后，旧视角下已经计算的行数和下载链接立即失效，必须按新视角重新请求。

导出前显示：

- 当前日期范围；
- 当前数据范围，例如“仅本人”“全单位”或“李静的服务记录”；
- 已应用的其他筛选；
- 预计导出行数；
- 字段版本；
- “CSV 含单位内部办件信息，请按单位数据管理要求保存”的提示。

### 6.2 筛选与上限

CSV 与看板复用数据视角、日期、笔录室、标签、关键词及其规范化逻辑，并额外提供明细状态筛选：

- `scope=self|overall|person`，由服务端按角色授权；
- `ownerId` 只在 admin 的 `scope=person` 下允许；
- `dateFrom` / `dateTo`；
- `roomId`；
- `status=active|cancelled`；
- `tagId`；
- `query`，只匹配当事人、案号、事项、备注。

单次日期跨度最多 366 天，单次最多导出 20,000 行。超过上限时返回稳定的 `EXPORT_TOO_LARGE`，告知用户缩小日期范围或增加筛选，不截断后假装完整导出。

### 6.3 固定字段

CSV 字段版本首版记为 `reservation-detail-v1`，列顺序固定：

1. 预约日期
2. 开始时间
3. 结束时间
4. 预约时长（分钟）
5. 笔录室
6. 预约人
7. 当事人
8. 案号
9. 事项
10. 标签
11. 备注
12. 状态
13. 创建时间
14. 最后修改时间
15. 取消时间

状态输出为稳定中文显示值“有效”或“已取消”，原始枚举仍保持 `active|cancelled`。技术时间戳导出为带时区的 UTC RFC3339，预约日期和时分保持服务器本地业务时间文本。

不得导出：内部预约 ID、用户 ID、笔录室 ID、revision、密码信息、session、CSRF、API token、secret、install_id、数据库路径、服务日志内容或其他运维标识。

### 6.4 文件兼容与安全

- 文件名：`办件明细_YYYYMMDD-YYYYMMDD_YYYYMMDD-HHMMSS.csv`；
- 编码：UTF-8 with BOM；
- 行结束：CRLF；
- 表头：中文且固定顺序；
- CSV 引号与转义遵循 RFC 4180；
- 空值输出为空单元格，不用“null”或“None”；
- 对去除前导空白后以 `= + - @` 开头的文本单元格，在原值前加单引号，阻止 Excel 公式执行；其后仍按 CSV 规则转义；
- 服务端必须设置下载响应的类型和安全文件名，前端不拼接 CSV 内容；
- 不在磁盘长期保存临时导出文件，不将导出内容写入日志或审计。

### 6.5 审计

每次导出生成一条最少必要的安全审计记录，例如 `report.csv_exported`，记录：

- 操作者 ID；
- 服务端最终解析的数据视角以及目标人员 ID（如适用）；
- 日期范围和筛选摘要；
- 字段版本；
- 行数；
- 发生时间；
- 结果 `success|failure` 与稳定错误码。

审计不记录当事人、案号、事项、备注或 CSV 正文。服务端只能确认响应已成功生成，不能宣称浏览器或用户已经把文件保存到磁盘。

## 7. 服务端与 API 设计

### 7.1 共同查询层

新增只读 reporting service，职责是：

1. 根据当前用户解析 `self|overall|person`，形成不可被后续筛选覆盖的授权范围；
2. 解析并规范化日期、笔录室、标签和关键词筛选；CSV 路径再解析明细状态；
3. 构造固定参数化 SQL，禁止接收列名、表名、排序 SQL 或用户 SQL；
4. 形成一份共同的“预约基础集合”；
5. 从同一集合计算看板聚合和 CSV 行；
6. 返回口径版本和服务器业务日期。

建议内部结构：

- `ReportScope`：服务端解析后的 `self|overall|person` 及允许的 owner 范围；
- `ReportFilters`：经过验证的筛选对象；
- `resolve_report_scope(actor, requested_scope, owner_id)`：先授权，后查询；
- `build_reservation_base_query(scope, filters)`：参数化基础查询；
- `get_report_overview(scope, filters)`：按指标版本返回个人或 overall 聚合；
- `count_report_rows(scope, filters)`：导出前计数与上限判断；
- `iter_report_rows(scope, filters)`：稳定排序的明细行；
- `render_csv_cell(value)`：统一空值、公式防护和 CSV 转义。

稳定排序建议为：预约日期、开始时间、笔录室名称、预约创建时间、稳定预约 ID。ID 只用于服务端消除同值排序不确定性，不进入 CSV。

### 7.2 建议 API

保留 `/api/v1`，产品小版本升级不另起 API 大版本：

- `GET /api/v1/reports/overview`
  - 接受 `scope`、admin person 视角的 `ownerId` 及共同筛选；
  - 返回服务端最终解析的 `resolvedScope`、`filters`、`metricVersion`、`generatedAtUtc`、`summary`、`weeklyTrend`、与当前视角匹配的诊断分布及 `exportRowCount`；
  - employee 只允许 `scope=self`；admin 允许 `overall|self|person`；
  - 无业务数据时返回合法空集合和可空比率，不返回 404。
- `GET /api/v1/reports/reservations.csv`
  - 使用与 overview 完全相同的 scope 解析和筛选；
  - 返回 CSV 附件；
  - 超过 20,000 行返回 `422 EXPORT_TOO_LARGE`；
  - employee 请求 overall、person 或携带他人 ownerId 时返回不泄露目标用户存在性的稳定 `403 FORBIDDEN`；
  - 日期、未知房间/标签和查询长度错误均使用现有统一 JSON 错误外形。

如果后续需要页面内明细预览，应另加有游标签名分页的 JSON 接口，不能让前端下载完整集合后自行分页。V2.2.0 首版不因“以后可能下钻”提前增加该接口。

### 7.3 性能与数据一致性

- 第一版直接查询当前 SQLite，不引入数据仓库、缓存副本或定时 ETL；
- 聚合查询应在一次只读数据库连接和一致性读取窗口内完成；
- 评估并只增加确有查询计划证据的索引，不能为看板盲目堆叠索引；
- 所有筛选参数有长度、枚举和日期跨度上限；
- CSV 先计数再导出，并在两步间接受极小的并发变化可能；响应同时返回或审计实际生成行数；
- 若严格快照在实测中确有必要，再使用同一读事务完成计数与迭代，避免长事务影响写入。

## 8. 前端实现方案

### 8.1 路由与能力

- 新增所有已认证用户可进入的路由 `data-center`；
- bootstrap permissions 增加 `viewReports=true`，并仅向 admin 提供 `viewOverallReports=true` 与 `viewOtherUserReports=true`；不在组件中散落 `role === 'admin'`；
- employee 页面固定为 `self`，不渲染人员选择器；admin 默认 `overall`，可切换 `self` 或选择某一人员；
- 前端每次都展示服务端返回的 `resolvedScope`，不能仅相信本地请求参数决定标题或导出范围；
- API 客户端定义独立的 report 类型，不能把聚合响应伪装成预约列表；
- 页面状态至少覆盖：加载、空数据、筛选错误、视角无权限、目标人员不可用、会话过期、服务不可用和导出过大。

### 8.2 交互约束

- 默认进入页面即可看到本月概览，不要求先配置图表；
- admin 切换人员时必须把姓名与部门作为当前视角标题，避免误把个人数据当 overall；
- 导出按钮附近持续显示“将导出：本人 / 全单位 / 某某”的范围说明；
- 筛选使用明确的“应用筛选”和“重置”，避免每输入一个字就发起全量聚合；
- 图表悬停不是唯一读数方式，键盘和屏幕阅读器可读取同一数值；
- 颜色只表达辅助差异，取消状态同时使用文字或线型；
- 1024×720 仍是正式桌面验收下限；窄窗口允许图表纵向堆叠，不产生文档级横向滚动；
- 尊重 `prefers-reduced-motion`，第一版不需要复杂图表入场动画；
- 导出按钮在请求中进入 disabled/busy，防止重复生成；失败不显示成功图标。

## 9. V2.2.0 累计升级交付模式

### 9.1 双交付物

同一个稳定版本从同一源代码提交生成两类客户交付物：

| 交付物 | 使用对象 | 行为 |
| --- | --- | --- |
| V2.2.0 完整安装包 ZIP | 尚未安装 V2 的新用户 | 固定根目录全新安装，不读取 V1 |
| V2.2.0 离线累计升级包 ZIP | 已安装受支持 V2 基线的用户 | 就地升级已登记的 V2 安装，保留全部现场数据 |

两者都使用完整解压后的顶层零参数 BAT，并在需要时触发 UAC。不得从 ZIP 预览直接运行。

首个生产升级包只支持**经过最终实机验收并冻结的 V2.1.0 精确基线**升级到 V2.2.0。不能把仍处于候选状态、字节尚可能变化的 V2.1.0 当成稳定升级起点。以后每个稳定目标版本都应能从列入支持矩阵的旧 V2 稳定基线直接升级，不要求用户依次安装所有中间补丁。

### 9.2 不采用网页更新

V2.2.0 不提供：

- 程序内联网检查或下载安装；
- 管理员网页上传 ZIP/BAT/PS1；
- 浏览器或 Flask 服务执行更新负载；
- 自动扫描磁盘寻找“可能的旧版本”。

网页上传并执行更新包会把本地管理页面变成高风险代码执行入口，也会让正在被替换的服务负责替换自己。更新继续由本机、离线、UAC 提权的独立工具完成。

## 10. 累计升级事务

现有 `installer/update_core.py` 继续作为身份、代际、负载保护和数据快照的共同基线，但必须从“非生产预检”补齐为完整状态机后，才能把 `PRODUCTION_UPDATE_SUPPORTED` 置为真并进入客户 payload。

### 10.1 更新前检查

1. 只从明确登记的固定 V2 安装根解析目标；
2. 校验安装根、`install_id`、产品代际 2、当前版本和安装清单；
3. 拒绝 V1、未知代际、未知 schema、比目标更新的版本和不在支持矩阵中的源版本；
4. 校验目标 payload 的 manifest、SHA-256、版本、代际、许可证、SBOM 和构建来源；
5. 拒绝 payload 携带或覆盖 `data/`、`backups/`、`logs/`、secret、安装身份、事务文件和现场版本文件；
6. 对 SQLite 执行只读打开、`quick_check`、外键检查、代际和 schema 检查；
7. 检查同卷 staging、回滚空间、磁盘余量、维护锁、服务/任务身份和文件占用；
8. 记录更新前服务、备份任务及相关 V2 进程是否正在运行；不停止未知进程。

任一预检失败都必须在写程序文件和停止服务之前退出。

### 10.2 更新执行顺序

1. 获取带安装身份和进程身份的独占维护锁；
2. 创建一次受验证的在线业务备份；
3. 在同卷回滚区保存程序快照、受保护数据树清单和必要现场状态；
4. 生成并持久化事务记录，阶段为 `prepared`；
5. 只停止已验证属于本产品的服务、任务和进程；
6. 在同卷 staging 完整展开并验证目标程序；
7. 原子或可回滚地替换程序、冻结运行时和静态前端；
8. 如目标版本确有 schema 迁移，按产品代际 2 的显式迁移逐步事务执行；V2.2.0 预计无需迁移；
9. 重新复核 DACL、程序清单、数据树和安装身份；
10. 按更新前运行状态恢复服务：原来运行则启动，原来停止则保持停止；
11. 执行 loopback `/healthz`、session/bootstrap 兼容性和最小只读业务检查；
12. 健康检查通过后最后写入 `版本.txt`、安装清单和更新回执，阶段进入 `version_committed`；
13. 清理 staging 和事务锁。回滚临时副本只在确认提交和稳定重启后删除；正常备份仍按既有轮转策略保留。

### 10.3 失败与回滚

在 `version_committed` 之前失败时，更新器必须恢复：

- 原程序文件以及新文件原先不存在的状态；
- `data` 全树，包括数据库、secret、安装信息和未知现场文件；
- 原配置、任务、防火墙和 DACL；
- 原版本文件与安装清单；
- 更新前运行状态。

回滚后再次执行数据库完整性、外键和安装身份检查。若自动回滚也失败，停止服务并进入明确的人工恢复状态，保留本地事务日志和回滚材料，不得继续尝试启动不确定版本。

在 `version_committed` 之后重跑时，只允许完成清理或复核，不能回滚已投入使用的新版本，更不能覆盖升级后新增的客户数据。

### 10.4 中断恢复与幂等

事务文件至少记录：事务 ID、安装根、install_id、源/目标版本、payload SHA-256、当前阶段、快照位置、更新前运行状态和提交时间。每个阶段重新进入时必须先检查已完成事实：

- 已复制且哈希一致的文件不重复盲写；
- 已完成的迁移不重复执行非幂等逻辑；
- 发现事务身份或 payload 不匹配时拒绝接管；
- 断电或进程退出后再次双击同一升级包，可以选择安全继续或回滚；
- 不同目标版本不得复用旧事务状态。

## 11. 安全、隐私与开源边界

- 看板和导出全部在本地 Flask + SQLite 内完成，不接入云统计、遥测或远程分析；
- 开源仓库、Issue、CI、截图和测试只使用合成数据，不上传客户数据库、CSV、日志、备份或真实个人信息；
- 浏览器永远不直接读取 SQLite 文件，服务端只提供固定白名单字段和聚合；
- CSV 是敏感业务输出，权限和审计不能仅靠页面入口；employee 的 owner 收窄条件必须由服务端强制注入；
- 图表不加载外部脚本、字体或资源；依赖必须兼容 Apache-2.0 分发并进入第三方许可证清单；
- 安装与升级包不携带数据库、secret、日志、备份、测试数据、`node_modules`、源码映射或开发工具；
- 更新日志只记录阶段、稳定错误码、文件摘要和技术状态，不记录预约正文、密码、token 或 secret；
- 未取得 Authenticode 证书前，候选包仍只能受控内部传递并带外核对 SHA-256。

## 13. 测试与验收矩阵

### 13.1 报告与 CSV 自动化

- employee 请求 self 看板与 CSV：只返回本人数据，且与本人历史明细对账一致；
- employee 伪造 `scope=overall|person`、他人 `ownerId`、游标或前端状态：稳定 403，响应不含他人是否存在、聚合数或明细；
- admin overall：返回全单位数据；admin person：只返回目标人员数据；两种视角切换后旧导出范围不可复用；
- 未登录：稳定 401；会话过期沿用现有重新登录流程；
- 日期边界：闰年、月末、366 天、超过 366 天、非法日期；
- 筛选：房间、人员视角、全局/个人标签、关键词及组合；overall 不接受个人标签；CSV 状态筛选独立验证；未知或禁用对象的约定必须固定；
- 指标：个人/overall、空集合、仅取消、仅有效、已结束/未结束边界、跨周、同值排序、多房间、多用户；
- 口径：个人看板与本人 CSV、admin person 与同一人员 CSV、overall 与全单位 CSV 分别对账；有效指标匹配有效行，取消辅助指标匹配已取消行；
- 快照：历史预约人和标签使用保存时快照，不被当前名称覆盖；
- CSV：BOM、CRLF、中文表头、逗号、引号、换行、超长文本、空值；
- 公式注入：前导空格后出现 `= + - @` 仍被防护；
- 隐私：内部 ID、revision、token、secret、路径不进入响应；
- 上限：20,000 行成功，20,001 行明确拒绝且不生成截断文件；
- 审计：成功/失败、筛选摘要、字段版本和行数正确，正文不进入审计。

### 13.2 前端验收

- 1024×720、1280×720、1440×900、1920×1080 无文档级横向滚动；
- employee 无人员选择器且始终显示“我的数据”；admin 默认 overall，选择人员后的姓名、部门、指标与导出范围同步更新；
- 初始、本月无数据、筛选无结果、加载失败、会话过期、视角无权限、导出过大状态完整；
- 键盘可操作筛选、图表读数替代内容和导出；焦点返回正确；
- 200% 浏览器缩放下核心信息和操作仍可用；
- 色彩不是唯一语义，文字对比度和 44×44px 操作目标符合现有合同；
- 干净会话控制台无错误/警告，业务请求无不必要的重复轮询；
- 图表与 CSV 不发起任何外网请求。

### 13.3 更新器自动化与实机验收

- 成功：冻结 V2.1.0 → V2.2.0，数据、账号、设置、日志、备份和未知 data 文件不变；
- 累计：每个列入支持矩阵的旧 V2 稳定基线可直接到目标版本；
- 身份：错误 install_id、V1、未知代际、未知/更新 schema、目标版本倒退全部拒绝；
- 负载：ZIP 损坏、manifest 不符、payload SHA 不符、携带受保护路径全部拒绝；
- 环境：UAC 取消、磁盘不足、目录被占用、端口被其他程序占用、维护锁竞争；
- 数据库：缺失、为空、损坏、外键错误、WAL/SHM 情形和备份失败；
- 故障注入：prepared、停服后、替换中、迁移中、健康检查前后、版本提交前后；
- 回滚：恢复文件存在/不存在状态、程序、data、DACL、任务和更新前运行状态；
- 幂等：中断后重跑同一包、提交后重跑、用不同目标包接管旧事务；
- 状态：升级前服务未运行时，升级后保持未运行；升级前运行时，健康通过后恢复运行；
- Windows：真实 Windows 10 x64 为首要门禁，同时覆盖 Windows 11、标准用户 + UAC、中文路径和普通杀毒软件环境；
- 局域网：升级后本机与第二台同网设备均能登录和读取业务页面；防火墙仍为 LocalSubnet；
- 签名：BAT/PowerShell/冻结运行时/关键可执行文件及最终 ZIP 的签名与哈希核验流程符合发布清单。

## 14. 明确不在 V2.2.0

- 任意数据库浏览、表编辑或 SQL 控制台；
- 浏览器下载原始 SQLite 数据库；
- 员工排行、绩效评价和人员画像；
- 缺少历史分母时的笔录室“利用率”；
- 新增到场、爽约、完成、材料补正、案件流程或期限提醒状态；
- AI 总结、预测、自动分类或自然语言查询数据库；
- 短信、微信、邮件、Windows 原生通知；
- 云看板、遥测、跨公网访问或多组织租户；
- 在线自动更新、网页上传更新包或服务端远程执行；
- V1 数据迁移、V1 目录扫描或 V1 更新包兼容；
- 动态插件系统；
- 为了图表而引入外部 CDN、非兼容模板或未经审查的运行时依赖。

## 15. V2.1.0 之后的升级模式

后续采用“**稳定核心 + 小主题版本 + 累计升级包**”模式：

- `V2.1.x`：只修复 V2.1.0 的缺陷和安全问题，不加入新的产品主题；
- `V2.2.0`：服务数据中心 + 办件明细 CSV + 第一代 V2 累计升级链路；
- `V2.2.x`：只修复数据中心和升级链路问题；
- `V2.3.0`：根据真实用户反馈选择一个新的、边界清楚的主题，例如到场/爽约/完成状态，但不预先承诺；
- `V3.0.0`：只有当部署模型、核心权限、多组织边界或数据合同发生真正代际变化时才启用，不把普通功能增加包装成 V3。

通用预约、报表、备份和安全能力继续进入核心产品。与特定办案流程深度绑定的办件台账、材料、期限、音视频或 AI 能力，等权限、审计、数据保护和实际需求成熟后，再评估作为独立模块或产品线；V2.2.0 不提前建设动态插件框架。

## 16. 开发启动前的最终确认项

本方案给出以下默认决定，若无异议即可按此拆卡：

1. 页面名称使用“数据中心”，导出操作使用“导出办件明细 CSV”；
2. employee 与 admin 都能进入；employee 只能查看和导出本人数据；
3. admin 默认进入 overall，也可选择本人或任一人员的个人面板；
4. 个人主指标为有效预约、已结束预约和预约时长；
5. overall 主指标为有效预约、已结束预约和预约总时长，取消率只作异常核查 guardrail；
6. overall 不显示全员工作负荷长列表；管理员通过顶部选择器查看个人面板，分析区一次只显示时段、笔录室或标签中的一个；
7. 默认本月，单次跨度 366 天，单次最多 20,000 行；
8. CSV 使用本方案列出的 15 个固定字段，字段版本为 `reservation-detail-v1`；
9. 第一版不做笔录室利用率百分比、案件数、服务人数或实际办理时长；
10. 第一版图表使用原创 React + SVG，不引入第三方模板或外部 CDN；
11. V2.2.0 保持数据库 schema v2，除非开发中出现经过评审、确实无法通过现有字段实现的需求；
12. V2.2.0 同时交付新装包和离线累计升级包，累计升级器不是网页功能；
13. 首个支持的升级源必须是最终冻结并通过实机验收的 V2.1.0；
14. 任何候选在 Windows 实机、回滚和签名门禁完成前，继续保持 `formal_external_release_allowed=false`。
