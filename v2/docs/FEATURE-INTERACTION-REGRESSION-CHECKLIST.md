## 1. 风险级别与通用判定

- `P0`：可能造成预约归属错误、越权、重复占用、数据丢失或不可恢复。
- `P1`：核心流程可完成，但状态、提示、统计或恢复行为会误导用户。
- `P2`：显示、焦点、响应式或低频边界问题。
- 所有写操作都应验证：界面状态、API 返回、数据库最终状态、事件时间线和安全审计五者一致。
- 失败时不得“界面显示成功、服务端其实失败”，也不得为了恢复而重复提交一次写操作。

## 2. 标准测试数据

建议每次从可恢复的基线数据库开始，固定以下角色和记录：

- A：启用的管理员；B：启用的普通员工；C：另一名普通员工；D：停用用户；E：第二名管理员。
- R1：启用且公开屏可见；R2：启用但公开屏隐藏；R3：已停用；R4：有未来预约、不能直接删除。
- Q1：B 创建的未来预约；Q2：A 创建的未来预约；Q3：已开始；Q4：已结束；Q5：已取消。
- Q6：B→C 待确认交接；Q7：B→C 已接受；Q8：交接发起后又被编辑；Q9：交接发起后又被管理员指派。
- N1/N2/N3：三条未确认预约变更；H1/H2/H3：三条待处理交接；U1：即将开始提醒。
- 文本边界：中英文混排姓名、很长部门名、很长当事人/事项/房间/标签名、空备注、最长备注和特殊字符。

## 3. 必须始终成立的业务不变式

- [ ] `P0` 预约当前归属只有一人，交接/指派成功只增加一次 revision。
- [ ] `P0` 人员候选列表排除“当前预约者”，而不是排除“当前操作人”。
- [ ] `P0` 管理员处理他人的预约时可以指派给自己；管理员处理自己的预约时不能指派给自己。
- [ ] `P0` 普通员工不能编辑、取消、交接或读取他人预约的受限细节。
- [ ] `P0` 已取消 > 交接中/已交接：取消后不再显示“交接中”。
- [ ] `P0` 已开始/已结束的预约不能新发起交接或指派。
- [ ] `P0` 失效、编辑或取消后的交接请求不得再改变预约归属。
- [ ] `P1` 当事人、预约者、操作人、交接发起人和接手人在文案与审计中不得混用。
- [ ] `P1` 个人标签、“我的预约”、即将开始提醒和统计口径对交接后归属有明确且一致的规则。
- [ ] `P1` 每一个待处理事项都只能被自己的动作消费：确认变更不得接受/拒绝交接，稍后处理交接不得确认变更。

## 4. 多条变更 + 多条交接的组合弹窗

### 4.1 数量与布局

- [ ] `P1` 0 变更 + 0 交接：不出现弹窗或排队提示。
- [ ] `P1` 1 变更 + 0 交接：保持单条变更的查看/确认流程。
- [ ] `P1` N 变更 + 0 交接：全部可见、可单条处理、可全部确认。
- [ ] `P1` 0 变更 + 1/N 交接：每条都有独立的接受/不接受操作。
- [ ] `P1` 1 变更 + 1 交接：标题和两个分区分别显示 `1 条`，总数不重复、不遗漏。
- [ ] `P1` 3 变更 + 3 交接：使用唯一内容滚动区，页头与页脚保持可见，不出现嵌套滚动。
- [ ] `P2` 10 + 10 压力数量：弹窗不超出视口，最后一条可通过键盘和鼠标到达。
- [ ] `P2` 超长当事人/事项/房间/部门：正常换行，按钮不被挤出弹窗。
- [ ] `P2` 1024×768、1366×768、2560×1440 均不出现横向滚动或被遮挡操作。
- [ ] `P2` 窄屏与 200% 缩放：页脚改为纵向，两个动作仍有清晰主次和至少 44px 点击高度。

### 4.2 动作隔离和失败恢复

- [ ] `P0` 点“交接稍后处理”只隐藏本次交接弹窗，预约变更仍留在弹窗中待确认。
- [ ] `P0` 点“确认全部变更”只写入变更回执，交接请求仍保留且可处理。
- [ ] `P0` 接受 H1 后只改变 H1 对应预约，H2/H3/N1/N2/N3 不受影响。
- [ ] `P0` 拒绝 H1 后预约仍归原预约者，其他事项不被消费。
- [ ] `P1` 单条变更的“查看预约”先成功确认该条，再打开正确预约；确认失败则不打开详情。
- [ ] `P1` “全部确认”中一条 API 失败：成功项不重复出现，失败项稍后重现，提示明确说明“部分失败”。
- [ ] `P1` 接受/拒绝交接时网络失败：不先行从列表移除，刷新后以服务端最终状态为准。
- [ ] `P1` 连续快速点击同一动作：只产生一次写入、一条事件和一条审计。
- [ ] `P1` 处理期间新一轮 poll 返回旧列表：不得将已处理项目短暂插回或覆盖新状态。

### 4.3 焦点、Esc 和层级

- [ ] `P1` 混合弹窗初始焦点落在安全的“交接稍后处理”，而不是“接受交接”。
- [ ] `P1` Tab/Shift+Tab 焦点始终留在弹窗内，背景为 inert 且读屏器不重复读取背景。
- [ ] `P1` 混合弹窗按 Esc：只暂后交接，不确认变更；弹窗转为变更模式后焦点依然正确。
- [ ] `P1` 纯变更弹窗按 Esc 的确认语义与可见文案一致。
- [ ] `P1` 纯交接弹窗按 Esc 只暂后处理，绝不自动接受或拒绝。
- [ ] `P1` 打开预约详情抽屉时，弹窗不与抽屉重叠，顶部排队条同时显示两类事项的准确数量。
- [ ] `P1` 关闭抽屉后排队弹窗立即出现，焦点不返回到已不存在的抽屉元素。
- [ ] `P2` 即将开始 toast、成功 toast、排队条和弹窗同时触发时，层级、aria-live 和关闭顺序不互相干扰。

## 5. 交接/管理员指派身份矩阵

### 5.1 候选人列表

- [ ] `P0` B 是 Q1 当前预约者，A 打开指派：候选人不包含 B，包含 A、C、E，不包含 D。
- [ ] `P0` A 是 Q2 当前预约者，A 打开交接：候选人不包含 A，包含 B、C、E，不包含 D。
- [ ] `P0` B 打开自己 Q1 的交接：不包含 B，不包含 D。
- [ ] `P0` C 伪造 Q1 的候选人目录请求：服务端返回 403，不泄露人员列表。
- [ ] `P0` 直接伪造 `toUserId=B`：即使前端被绕过，服务端仍返回 422，归属不变。
- [ ] `P0` 直接伪造停用/不存在用户 ID：服务端拒绝，不建立待处理请求。
- [ ] `P1` 抽屉打开后 B 被停用或 Q1 被改为 C 所有：旧候选人不得无提示提交，应刷新或给出可恢复冲突。
- [ ] `P2` 同名用户用部门辅助区分，选中状态不依赖显示名而依赖稳定 ID。

### 5.2 交接与指派结果

- [ ] `P0` B→C：发起后仍归 B，C 接受后才转给 C。
- [ ] `P0` B→C：C 拒绝后仍归 B；B 主动撤回后 C 不再可处理。
- [ ] `P0` A 将 B 的 Q1 指派给 C：立即生效，不生成 C 待确认请求，但 C 收到不可拒绝的“管理员指派”知晓通知。
- [ ] `P0` C 的管理员指派通知只有“查看预约 / 我知道了”，不得出现“不接受”；确认只写回执，不再次修改 owner 或 revision。
- [ ] `P0` 关闭两项提醒偏好后，管理员指派通知仍然出现；确认后不再重复出现。
- [ ] `P0` A 连续把 Q1 指派给 C、再指派给 E：C 不再看到“预约已转入你名下”，只有当前预约者 E 看到最新结果。
- [ ] `P0` A 将 B 的 Q1 指派给 A：立即生效，ownerId/owner 快照/revision/事件/审计全部一致。
- [ ] `P0` A 与 E 同时指派同一预约：不得丢失更新，最终仅一个归属，竞态结果可解释。
- [ ] `P0` C 在 A 同时编辑/取消时接受：只有一个写操作成功，另一个收到 revision/状态冲突。
- [ ] `P1` 交接成功后旧预约者的“我的预约”、新预约者的“我的预约”、历史和日历在一次刷新内收敛。
- [ ] `P1` 交接后再指派回历史创建者的产品语义得到明确确认；当前规则只排除“当前预约者”。

## 6. 交接与预约生命周期叠加

- [ ] `P0` 有待交接请求时编辑日期、时间、房间、当事人、事项或标签：旧请求必须明确失效或要求重新发起。
- [ ] `P0` 有待交接请求时取消：交接弹窗、工作交接页、历史状态全部不再显示待处理。
- [ ] `P0` 交接等待期跨过预约开始时刻：接受被拒绝，预约归属不变。
- [ ] `P0` 系统工作时间修改后，已有预约和已发起交接不被静默改写。
- [ ] `P0` 房间停用/删除预检与待交接预约并存：阻塞列表可直达正确记录，不破坏交接状态。
- [ ] `P1` 交接成功后立即进入提醒窗口：即将开始提醒只发给新预约者。
- [ ] `P1` 旧预约者已打开详情时发生交接：下一次写操作被权限/revision 校验阻止，不覆盖新归属。
- [ ] `P1` 交接后管理员编辑：变更通知发送给正确的当时预约者，文案中当事人和预约者不混淆。
- [ ] `P1` 连续 B→C→A 交接：事件时间线顺序、每次 before/after owner 和审计 actor 均正确。

## 7. 本次源码审查揭示的优先深测风险

以下不等于本次已修复，应先用自动化用例固定期望，再决定是否改产品语义：

- [x] `P0` **管理员强制指派覆盖待交接请求**：Q9 的旧 pending request 在同一事务内收敛为 withdrawn，不再在 C 的弹窗或工作交接页显示可接受（后端自动化已固定）。
- [ ] `P0` **旧 revision 的待交接请求**：Q8 在读列表/提醒时就应表现为已失效，而不是等 C 点“接受”后才报冲突。
- [ ] `P0` **变更通知受众随当前 owner 漂移**：交接前发生但未确认的变更，交接后不得错发给当时并非预约者的新 owner，也不得让原 owner 无法收尾。
- [ ] `P1` **变更通知与交接的时序**：同一分钟内先编辑后交接、先交接后编辑，受众和时间线都要符合当时所有权，不能只看最终 owner。
- [ ] `P1` **个人标签归属**：管理员编辑他人预约与交接后再编辑时，可选标签应始终属于当前 owner，而非 actor 或历史创建者。

- [ ] `P1` **停用用户的未来预约**：停用 owner 后预约谁来接管、谁收提醒、是否要强制管理员处理，不得静默变成无人能操作的记录。
- [ ] `P1` **暂后处理的生命周期**：页面刷新、重新登录、会话恢复后是否应再弹，需有明确口径，并与“工作交接”徽标一致。

## 14. 推荐的组合测试法

对每个新功能，不只测“自己的主路径”，至少跑以下 pairwise/triple 组合：

- [ ] 角色（管理员/员工） × 记录归属（本人/他人） × 记录状态（active/started/ended/cancelled/pending handover）。
- [ ] 用户状态（启用/停用/角色变更） × 操作阶段（打开前/打开后/提交中/提交后）。
- [ ] 通知数量（0/1/N） × 通知类型（变更/交接/即将开始） × 前台容器（主页/抽屉/弹窗/toast）。
- [ ] 并发动作（编辑/取消/交接/指派/停用用户/停用房间）的两两组合。
- [ ] 网络（正常/慢/中断/恢复） × 写入阶段 × poll 刷新时机。
- [ ] 时间（开始前/恰在开始时刻/已开始/结束时刻/跨天边界） × 服务器时钟 × 浏览器时区。

## 15. 发布前最小门禁

- [ ] 后端全量测试、前端 lint/test/build 全部通过，无新增 warning（已知 bundle-size warning 另行记录）。
- [ ] 上述 P0 全部自动化或有可复现的人工证据，无未解释 FAIL。
- [ ] 真实浏览器完成 3+3 混合弹窗、管理员指派给自己、交接接受/拒绝三条主流程。
- [ ] 新数据库首次安装、旧 V2 schema 升级、备份/恢复和进程重启各至少一次。
- [ ] 普通 Windows 用户物理机完成安装、重启、多账号、局域网访问和卸载/数据保留验收。
- [ ] 检查发布物不包含测试数据库、密码、本机路径、截图、临时日志或开发依赖。
- [ ] 正式外发、签名、tag 和 SHA 门禁均明确通过；候选包不得被误标为已正式发布。
