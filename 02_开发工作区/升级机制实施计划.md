# 会议室预约系统 — 一键升级机制实施计划（评审修订版）

> 本文档是完整实现说明书。实现者无需任何对话上下文，只读本文件和代码库即可开工。
> 本版已补齐自解压边界、累计升级、并发锁、断电恢复、数据库回滚和启动验证。

## 0. 背景与目标

会议室预约系统 V1.0.0 已交付客户并冻结（见 `01_版本归档/`，只读，禁止修改）。
客户使用一台长期开机的 Windows 10/11 机器，部署形态为“解压即用”文件夹（参考
`02_开发工作区/Windows部署目录-V1.0.0/`），客户操作按“10 岁小孩也能完成”设计。

**目标**：建立一套与具体业务升级内容无关的一键升级通道。今后每次发版，维护者在
Mac 上运行生成脚本，产出一个自解压 BAT 文件；客户只需双击这一个文件，看到
“升级成功”即完成。

“数据不受影响”的准确含义：

- 绝不删除、覆盖或遗失客户账号、会议室、预约、会话密钥和首次登录信息；
- 数据库迁移可以修改 `data\reservation.db` 的结构或内容，但升级前必须制作可验证的
  完整快照，失败或中断后必须恢复原数据；
- `backups\` 中的既有备份不读取、不覆盖、不删除；
- `logs\` 中的既有日志不覆盖、不删除，升级器只新增一份升级日志；
- `runtime\` 本期完全不修改。

非目标：不做联网自动更新；不把系统暴露到互联网；不改变 V1.0.0 业务功能；不做安装
向导或 EXE 安装包；不支持本期内更新内嵌 Python 及第三方依赖。

## 1. 现状事实与铁律

### 1.1 客户侧部署结构

```text
D:\会议室预约系统\            （安装目录位置不固定）
├── ① 启动系统.bat
├── ② 立即备份.bat
├── ③ 设置开机自动启动.bat
├── ④ 停止本次后台系统.bat
├── ⑤ 取消开机自动启动.bat
├── 使用说明.txt
└── _程序文件\
    ├── app.py  server.py  backup.py  requirements.txt
    ├── runtime\            （Python 3.13 embeddable + 现有依赖）
    ├── static\  templates\
    ├── logs\server.log
    ├── data\               （客户数据）
    ├── backups\            （日常备份，保留 30 份）
    ├── 版本与校验信息.txt
    └── 给网管的首次验收清单.txt
```

关键事实：

- `_程序文件\runtime\python.exe` 可直接运行维护脚本，不依赖客户机器的 Python。
- `server.py --check`：检测到本系统运行时退出 0，否则退出 1。
- `init_db()` 当前创建 V1.0.0 基线表；数据库已有 `app_meta(key, value)`。
- SQLite 使用 WAL、外键和显式写事务。
- 计划任务名固定为 `会议室预约系统`。
- 开发机是 macOS，BAT/PowerShell 的最终执行必须在 Windows 10/11 验证。

### 1.2 不可违反的规则

1. `01_版本归档/` 永远只读。
2. 升级器不得修改 `runtime\`、既有 `backups\` 或既有 `logs\`。
3. 升级包必须是**完整累计包**：任意受支持的较旧版本均可直接升级到目标版本，不能依赖
   客户先安装中间版本。
4. 同一时刻只允许一个升级进程；重复双击时，第二个窗口提示“升级正在进行”。
5. 已装版本大于或等于包版本时正常退出 0；只有 V1.0.0 缺失 `版本.txt` 可按 1.0.0
   处理，文件存在但内容非法必须报错，不能猜测。
6. 修改受管业务程序或数据库前必须完成并验证回滚快照。停机前允许先写入只记录运行状态的
   `preparing` 恢复意图；该状态不授权覆盖程序或数据。
7. 覆盖、迁移、自检、重新启动、健康检查、最终版本提交中的任一步失败，都要自动恢复旧
   程序和旧数据。
8. `版本.txt` 是升级事务的最后提交点；健康检查成功前不得覆盖安装目录中的版本文件。
9. 发生断电、窗口被关或进程被杀后，下次运行升级包必须先发现未完成事务并恢复，再重新
   升级，不能把半成品当成成功版本。
10. `版本.txt` 提交后必须持久化 `version_committed` 阶段。此阶段及“版本已提交但阶段
    尚未来得及更新”的原子交接窗口只能安全收尾，任何情况下不得回滚程序或 `data`。

## 2. 总体设计

```text
维护者 Mac：                                客户 Windows：
完整累计负载 ── 制作升级包.py ──▶ 单个 BAT ── 双击/UAC
     │                                      │
     ├─ 完整受管文件                        ├─ 校验自身与负载
     ├─ 版本号                              ├─ 定位安装目录、加独占锁
     └─ SHA-256                             ├─ 处理上次未完成事务
                                            ├─ 持久化 preparing、停止系统
                                            ├─ 验证数据
                                            ├─ 程序+data 回滚快照
                                            ├─ 覆盖（暂不提交版本）
                                            ├─ 迁移、自检、启动、健康检查
                                            └─ 最后提交版本并宣布成功
```

BAT 仍由三段组成，但两个标记必须是文件中的**独占完整行**：

```text
（BAT stub）
__UPGRADE_PS1_BELOW__
（仅 PowerShell 源码）
__UPGRADE_PAYLOAD_BELOW__
（仅 Base64 ZIP）
```

重要实现约束：

- stub 不能用普通 `IndexOf("__UPGRADE_PS1_BELOW__")`，因为标记文字会先出现在
  stub 自己的查找语句中。
- 必须使用多行正则匹配“整行标记”，并断言两个标记各只匹配一次、顺序正确。
- 写入临时 `.ps1` 的内容只能是两个标记之间的文本，绝不能把 Base64 一并写入 PS1。
- PowerShell 从原 BAT 的第二个整行标记之后提取 Base64。
- 生成器必须自动验证最终 BAT 中两个整行标记各出现一次，并反向解包校验哈希。

## 4. 版本、负载与兼容规则

### 4.1 版本文件

- `_程序文件\版本.txt`：UTF-8 无 BOM，内容严格为 `X.Y.Z`，允许末尾一个换行。
- V1.0.0 没有此文件；**仅缺失时**视为 1.0.0。
- 空文件、非法格式、带额外文字均报错并停止，不修改安装目录。
- PowerShell 使用 `[version]` 比较；Python 使用整数三元组比较，不允许字符串比较。
- Payload 内的版本、PS1 内嵌版本、生成器参数必须三者一致。
- 升级过程先将新版本文件留在临时 Payload 中；迁移和启动验证完成后，才通过
  “临时文件 + 同卷原子替换”提交到安装目录。

### 4.2 完整累计负载

每个正式升级包必须包含以下完整受管集合，而不是只放发生变化的文件：

```text
① 启动系统.bat
② 立即备份.bat
③ 设置开机自动启动.bat
④ 停止本次后台系统.bat
⑤ 取消开机自动启动.bat
使用说明.txt
_程序文件/app.py
_程序文件/server.py
_程序文件/backup.py
_程序文件/migrate_check.py
_程序文件/requirements.txt
_程序文件/版本.txt
_程序文件/static/**
_程序文件/templates/**
```

除此之外的任何路径一律拒绝。以下名称在路径任意层级出现均拒绝（Windows 路径按大小写
不敏感处理）：

```text
data  backups  logs  runtime  _升级回滚  _升级状态.json  _升级锁
```

生成器和 Windows 升级逻辑都必须：

- 规范化相对路径并拒绝 `..`、绝对路径、盘符路径、NTFS ADS 和重解析点/符号链接；
- 执行精确白名单和黑名单校验；顶层 BAT 使用精确文件名，不使用 `①*.bat` 一类宽泛匹配；
- 要求 `static`、`templates` 非空；
- 拒绝重复路径及仅大小写不同的重复路径；
- 校验 Payload 中 `requirements.txt` 与 V1.0.0 冻结依赖清单一致。本期不能加入内嵌
  runtime 中不存在的新依赖；如需更新依赖，应另立 runtime 升级方案。

`_程序文件\__pycache__` 是可丢弃的 Python 运行缓存，不属于累计 Payload，也不进入程序
快照。安装新程序后、迁移前，以及回滚恢复旧程序后、重新启动前，升级器必须精确删除这
一个根层缓存目录（先拒绝重解析点），避免跨版本误用时间戳仍然匹配的旧 `.pyc`。

### 4.3 Payload 完整性

- 生成器先制作 ZIP，再计算 ZIP 的 SHA-256。
- `$PackageVersion` 和 `$PayloadSha256` 由生成器写入 PS1 占位符。
- Windows 端必须在停系统之前完成 Base64 解码、SHA-256 比对、解压和双重路径校验。
- SHA-256 用于发现传输损坏或误编辑，不把它描述成数字签名；客户只运行维护者通过约定
  渠道发送的文件。

## 5. 数据库迁移框架

### 5.1 app.py

在不改路由和业务逻辑的前提下新增：

```python
SCHEMA_VERSION = 1
MIGRATIONS: list[tuple[int, Callable[[sqlite3.Connection], None]]] = []
```

`_migrate_schema(db)` 规则：

1. `app_meta` 中无 `schema_version` 时视为 V1.0.0 基线 1，并在事务中写入 1。
2. `MIGRATIONS` 保存从 2 开始的完整迁移历史；目标编号必须唯一、严格递增且连续，完整
   集合必须等于 `2..SCHEMA_VERSION`。
3. 数据库版本大于代码的 `SCHEMA_VERSION` 时立即失败，禁止旧代码猜测性运行。
4. 每个迁移在独立的 `BEGIN IMMEDIATE` 事务中执行，迁移内容和对应
   `schema_version` 更新必须在同一事务提交；失败则回滚该事务并抛出异常。
5. 迁移只能加表、加列、加索引或插入/更新数据；禁止删表删列。迁移必须幂等，不能使用
   会隐式提前提交的写法。
6. `init_db()` 继续先建立 V1.0.0 基线并执行原有 seed，再调用 `_migrate_schema(db)`。
   新装库也从基线依次应用完整迁移历史。

“只做向前兼容迁移”降低旧代码读取新库的风险，但不替代升级器的数据快照；升级失败时
仍必须恢复升级前数据库。

### 5.2 migrate_check.py

支持两种模式：

```text
runtime\python.exe migrate_check.py --precheck <数据库路径>
runtime\python.exe migrate_check.py --migrate
```

`--precheck` 不导入业务 `app`，只使用标准库 SQLite：

- 打开指定数据库并执行 WAL checkpoint；
- 执行 `PRAGMA integrity_check` 和 `PRAGMA foreign_key_check`；
- 任何异常或非空外键错误均退出 1。

升级覆盖前，可从临时 Payload 中运行该脚本，对已安装数据库做预检。

`--migrate`：

- 将工作目录切到脚本所在 `_程序文件`；
- `from app import app, init_db, SCHEMA_VERSION` 并执行 `init_db()`；
- 再执行完整性检查和外键检查；
- 要求数据库 `schema_version == SCHEMA_VERSION`；
- 成功打印简短中文结果并退出 0；失败打印中文错误、写入升级日志并退出 1。

## 6. Windows 升级事务

### 6.1 提权与退出码

BAT stub 开始时先检测管理员权限。非管理员时：

- 使用 `Start-Process -Verb RunAs -Wait -PassThru` 重新运行 BAT；
- 原窗口等待管理员子进程结束，并原样传回子进程退出码；
- 用户取消 UAC 时提示“升级未开始，未修改任何文件”，退出码 3；
- 禁止使用“启动管理员窗口后，原窗口立即按成功退出”的模式。

约定退出码：0 成功或无需升级；1 升级失败但已恢复；2 用户取消选择目录；3 UAC
取消；4 另一个升级正在进行；5 发现未完成事务但自动恢复失败。

### 6.2 定位、锁与上次中断恢复

管理员进程完成 Payload 校验后定位安装目录，顺序如下：

1. BAT 所在目录；
2. `D:\会议室预约系统`、`C:\会议室预约系统`、`E:\会议室预约系统`；
3. 当前用户桌面和下载目录下的 `会议室预约系统`；
4. 弹出文件夹选择框，提示用户选择会议室预约系统目录。

候选目录必须同时存在 `_程序文件\app.py`、`_程序文件\server.py` 和
`_程序文件\runtime\python.exe`。如果上次回滚中断、受管程序暂时不完整，只要仍存在
`_程序文件\runtime\python.exe` 和 `_程序文件\_升级状态.json`，也必须允许定位并进入
严格的状态/快照恢复。用户取消选择时退出 2，无任何修改。

定位后立即以 `_程序文件\_升级锁` 打开独占文件句柄（`FileShare.None`）：

- 无法取得时提示“升级正在进行，请不要重复打开”，退出 4；
- 锁依靠进程句柄释放，不以“锁文件是否存在”判断，避免崩溃后永久锁死。

定位后先拒绝与受管文件重叠的升级 BAT 路径；取得锁后，**先检查
`_程序文件\_升级状态.json`，再检查版本号**。若存在未完成事务：

1. 若阶段为 `preparing`，程序和数据尚未覆盖，只按记录幂等恢复原运行/停止状态；
2. 若阶段为 `version_committed`，或阶段仍为 `healthcheck_passed` 但安装目录
   `版本.txt` 已严格等于该事务包版本，只核对版本、按需检查当前服务并删除状态文件；
   不改变用户此后可能手动调整过的运行/停止状态，不得回滚程序或 `data`；
3. 其他未提交阶段根据状态文件定位已经验证过的回滚快照；
4. 停止属于本安装目录 runtime 的残留进程；
5. 精确恢复旧程序与完整 `data`；
6. 执行数据库预检；
7. 根据状态文件中的 `WasRunning` 恢复旧系统并做健康检查；
8. 恢复成功后删除状态文件，然后才开始本次升级；恢复失败退出 5，保留快照和日志。

状态文件使用临时文件 + `Move-Item` 同卷替换，至少记录：事务 ID、包版本、快照路径、
当前阶段、原版本、`WasRunning`、`TaskExists`。停机前先原子创建 `preparing` 状态，
`SnapshotPath` 为空；回滚快照验证成功后，再以 copy-on-write 原子转为
`snapshot_ready` 并写入快照路径。失败处理必须依据重新读取的磁盘 durable state 分支，
不能依据尚未落盘的内存阶段启动破坏性回滚。`snapshot_ready` 持久化前不得覆盖程序和数据。

### 6.3 正常升级步骤

严格按以下顺序执行：

1. **检查版本**：缺失 `版本.txt` 视为 1.0.0；非法格式报错；已装版本大于或等于包版本
   时退出 0。
2. **检查空间**：在停机前估算 Payload、受管程序树、完整 `data` 快照和安全余量所需空间；
   空间不足直接退出，不修改安装目录。
3. **记录原运行状态和恢复意图**：在停止任何进程之前执行 `server.py --check` 得到
   `WasRunning`，独立记录计划任务是否存在 `TaskExists`，再原子写入 `preparing` 状态。
4. **停止系统**：存在计划任务则尝试 `schtasks /End`；再枚举 `python.exe/pythonw.exe`，
   只强制结束 `ExecutablePath` 位于本安装目录 `_程序文件\runtime` 下的进程。最多等待
   10 秒，直到 `server.py --check` 返回未运行；失败则退出，此时尚未修改数据和程序。
5. **数据库预检**：从临时 Payload 运行 `migrate_check.py --precheck`。数据库不完整时停止
   升级，保留原文件并提示联系维护人员。
6. **建立回滚快照**：创建
   `_程序文件\_升级回滚\<事务ID>\program` 和 `data`：
   - 对完整受管程序集合记录“原来存在/不存在”，复制所有原有文件；
   - 完整复制 `_程序文件\data`，包括隐藏文件；
   - 对快照中的数据库再次执行预检；
   - 数据库预检关闭连接后，为快照生成相对路径、长度和 SHA-256 清单，并逐项验证；
   - 任一步失败均退出，不能开始覆盖。
7. **提交快照状态**：以 copy-on-write 原子写入阶段 `snapshot_ready` 和快照路径；写盘
   失败时磁盘与内存都继续按 `preparing` 处理，只恢复原运行状态，不启动完整回滚。
8. **覆盖程序**：
   - 覆盖前重新核对临时 Payload 的精确文件集合、长度和 SHA-256；
   - 精确复制全部受管顶层文件和 `_程序文件` 文件，但暂不复制 `版本.txt`；
   - `static`、`templates` 用 `/MIR` 与累计 Payload 对齐；
   - 精确删除根层 `_程序文件\__pycache__`，再按 Payload 清单核对覆盖后的受管文件集合、
     长度和 SHA-256；
   - 除上述可丢弃缓存外，白名单外路径不得创建、修改或删除；
   - 每个 `robocopy` 返回码 0–7 视为成功，8 及以上视为失败；
   - 完成后把事务阶段更新为 `program_replaced`。
9. **迁移与自检**：在安装目录运行新 `migrate_check.py --migrate`，成功后更新阶段
   `migration_complete`。
10. **启动并健康检查**：
    - `WasRunning=true` 且 `TaskExists=true` 时用 `schtasks /Run`；原来手动运行时重新启动
      `① 启动系统.bat`；
    - `WasRunning=false` 时也要用安装目录的 runtime 临时启动新版服务，以验证新版确实能
      运行；健康检查完成后停止这个临时进程，使系统恢复为升级前的“未运行”状态；
    - 最多等待 30 秒，循环执行 `server.py --check`；
    - 健康检查成功，并且最终运行/停止状态与升级前一致后，更新阶段
      `healthcheck_passed`。
11. **最终提交版本**：将 Payload 的 `版本.txt` 复制到安装目录临时文件，重新校验内容，
    再同卷原子替换正式 `版本.txt`。
12. **持久化已提交阶段**：版本提交后立即将状态原子更新为 `version_committed`。
    若恰好在版本文件提交与阶段更新之间中断，下次运行通过状态中的包版本与正式
    `版本.txt` 严格相等识别为已提交；从版本提交成功开始，任何清理错误都不得进入回滚。
13. **完成事务**：删除 `_升级状态.json`，写日志并显示
    “升级成功！当前版本 Vx.y.z”。回滚快照保留，不自动清理。

所有可能修改安装目录的步骤使用 `try/finally` 保证日志和锁句柄关闭。临时解包目录可在
成功或已恢复失败后清理；若恢复失败则保留，方便维护人员诊断。

### 6.4 统一回滚

步骤 8 之后任何异常都进入同一个回滚函数，不允许各步骤各写一套不一致的恢复代码：

1. 停止本安装目录 runtime 下的新旧残留进程；
2. 删除升级包可能创建的**精确受管文件和目录**；
3. 按快照清单恢复原程序；原来不存在的 `版本.txt`、`migrate_check.py` 等必须恢复为
   “不存在”，不能残留；
4. 精确删除根层 `_程序文件\__pycache__`，确保随后加载的是刚恢复的旧源码；
5. 将当前 `data` 移到同一事务目录下的 `failed-data` 供诊断，再从快照完整恢复原
   `data`；不得直接覆盖唯一快照；
6. 校验恢复文件的长度和 SHA-256，并执行数据库预检；
7. 仅当 `WasRunning=true` 时恢复旧系统，并等待旧系统健康检查通过；
8. 成功后删除 `_升级状态.json`，保留快照、failed-data 和升级日志；
9. 显示“升级失败，已自动还原，您的数据没有受影响”，退出 1。

如果回滚本身失败，不得显示“已还原”；应显示“自动恢复没有完成，请不要继续操作，并把
整个会议室预约系统文件夹交给维护人员”，退出 5，同时保留状态文件和所有快照。

## 7. BAT 与 PowerShell 模板要求

### 7.1 BAT stub

模板只负责：设置 UTF-8、提权并等待、按整行标记抽取纯 PS1、运行 PS1、传递退出码、
显示最终简短提示。示意算法：

```powershell
$all = [IO.File]::ReadAllText($batPath)
$psMatches = [regex]::Matches($all, '(?m)^__UPGRADE_PS1_BELOW__\r?$')
$payloadMatches = [regex]::Matches($all, '(?m)^__UPGRADE_PAYLOAD_BELOW__\r?$')
# 两者必须各一个，且 ps 标记在 payload 标记之前
# 只截取 ps 标记末尾到 payload 标记开头之间的内容
```

stub 在真正的 PS1 标记行之前必须显式执行 `exit /b %RC%`；非管理员父进程等待提权子进程
结束后也必须直接退出，不能继续在父进程中重复执行升级逻辑。

临时 PS1 文件名必须包含当前 PID，不能固定为 `meetingroom_upgrade.ps1`，避免并发互相覆盖。
BAT 和最终拼接文件使用 UTF-8 无 BOM、CRLF；从 BAT 抽出的临时 PS1 必须写成带 BOM 的
UTF-8（或 UTF-16LE），保证 Windows PowerShell 5.1 不会按本地 ANSI 误读中文路径。

### 7.2 PowerShell 5.1 兼容

- 只使用 Windows 10/11 自带 PowerShell 5.1、robocopy、schtasks 和 .NET API。
- 脚本开头启用严格模式，外层设置 `$ErrorActionPreference = 'Stop'`。
- 所有外部命令显式检查退出码，尤其不能把 robocopy 的 1–7 当失败。不得在全局
  `$ErrorActionPreference='Stop'` 下用 `2>&1` 直接调用 native command；Windows
  PowerShell 5.1 会把正常 stderr 包成 `NativeCommandError`，应使用独立进程捕获输出和
  真实退出码，或在严格限定范围内恢复错误策略。
- 路径一律使用 `Join-Path` 和参数数组，不能靠字符串拼接执行命令。
- 日志写入 `_程序文件\logs\upgrade-yyyyMMdd_HHmmss.log`；用户界面只显示短句，技术
  细节写日志。

## 8. 制作升级包.py

用法：

```text
python3 制作升级包.py <完整负载目录> <X.Y.Z> [--out 输出.bat]
```

行为：

1. 校验版本号、完整受管集合、精确白名单、递归黑名单、路径规范、符号链接和重复路径。
2. 校验 Payload `版本.txt` 与参数一致，`requirements.txt` 与冻结 runtime 兼容。
3. 以确定性顺序打 ZIP；ZIP 中只使用 `/` 分隔的相对路径。
4. 计算 ZIP SHA-256，将版本和哈希替换到 PS1 明确占位符；占位符必须各出现一次。
5. Base64 每行 76 字符。
6. 拼接 stub、PS1 标记、纯 PS1、Payload 标记、Base64。
7. 输出 UTF-8 无 BOM、CRLF 的 `升级到V<版本号>.bat`。
8. 重新读取生成文件：按整行标记拆分、确认标记数量与顺序、解 Base64、复核 SHA-256、
   解 ZIP 并逐文件比对源 Payload；任一步失败则不交付成品。
9. 打印版本、文件数量、文件清单、ZIP 哈希和最终大小。

## 9. 测试与验收

### 9.1 Mac 自动测试（必须全绿）

`tests/test_app.py` 新增：

- 新库初始化后 `schema_version == SCHEMA_VERSION`；
- V1.0.0 形态数据库写入基线版本且原数据不变；
- 多个迁移按序执行、重复初始化不重复改变数据；
- 迁移失败时迁移内容与版本号在同一事务回滚；
- 迁移编号重复、缺号、乱序或最高编号不匹配时失败；
- 数据库版本高于代码版本时失败；
- `migrate_check.py --precheck/--migrate` 的成功与失败退出码。

`升级包工具/tests/test_package_builder.py` 新增：

- 生成文件两个整行标记各一个且顺序正确；
- stub 抽出的 PS1 不包含 Payload 标记或 Base64；
- Base64 可逆、ZIP SHA-256 正确、解包后逐文件哈希一致；
- 最终文件 UTF-8 无 BOM、全部 CRLF；
- 缺文件、多文件、黑名单、`..`、绝对路径、大小写重复、符号链接、非法版本、版本不一致、
requirements 不兼容均被拒绝；
- 生成器输出可重复验证。

运行现有全部业务测试，不能删改原有断言来换取通过。

### 9.2 Windows 自动/半自动验证

Mac 的结构测试不能替代 Windows 执行。首次发版前必须在干净 Windows 10/11 虚拟机中：

- 真实双击生成后的 BAT，确认提权、PS1 解析和 Payload 解包可执行；
- 用测试副本执行成功、无需升级和失败回滚三条主路径；
- 保存日志和测试结果。条件允许时将这些步骤固化为 PowerShell 测试脚本。

### 9.3 Windows 人工验收清单

从 `Windows部署目录-V1.0.0` 复制测试安装，造用户、会议室和预约数据，并保存升级前
文件/数据库哈希。逐项验证：

1. BAT 放桌面升级成功；旧用户、会议室、预约和会话密钥全部保留。
2. 再次运行同一 BAT 提示无需升级，退出 0。
3. V1.0.0 缺少 `版本.txt` 时能升级；非法版本文件会安全停止。
4. 语法错误的新 `app.py` 触发回滚；受管文件树和数据库恢复为升级前哈希。
5. 数据库迁移中途故意失败，确认数据库也恢复，不只是代码恢复。
6. 新版服务无法启动时不能显示成功，并能恢复旧服务。
7. 计划任务存在且原来运行：升级后恢复运行。
8. 计划任务存在但原来未运行：升级后仍不擅自启动。
9. 手动启动且无计划任务：升级后恢复手动运行。
10. BAT 放安装目录、桌面、D 盘根目录分别测试定位。
11. 连续双击两次，第二个进程只提示升级正在进行。
12. 取消 UAC、取消选目录、磁盘空间不足、锁定文件时均在修改前安全退出。
13. 分别在“preparing 写入后但尚未停机、停机/快照期间、程序覆盖后、迁移后、健康检查后、
    回滚删除受管程序后”模拟终止；下次运行都能识别原目录，先按 durable state 恢复，再升级。
    另在 `version_committed` 写入后终止并新增一条预约，再次运行时必须保留新增数据，仅清理
    残留状态；同时覆盖“版本文件已提交、阶段仍为 healthcheck_passed”的原子交接窗口。
14. 从 V1.0.0 直接升级到一个模拟的后续累计版本，确认无需中间包。
15. 微信传输后确认文件未被改名/截断，并记录 SmartScreen 实际提示和客户操作文案。

### 9.4 负载示例

V1.0.1 示例负载必须是第 4.2 节规定的完整累计负载。`③④⑤` 的具体业务修订另行确定，
但无论哪些文件实际改变，示例包都要包含全部受管文件，用于验证跨版本累计升级。

## 10. 维护者出包流程

写入 `README-出包说明.txt`：

1. 在源代码工作区改代码；涉及数据库结构时追加迁移并更新 `SCHEMA_VERSION`。
2. 更新 `版本.txt`；确认没有新增 runtime 依赖。
3. 运行全部业务、迁移和生成器测试。
4. 从当前完整发布树组装完整累计 Payload，不从客户数据目录复制任何内容。
5. 运行生成器并记录输出 SHA-256。
6. 在 Windows 测试副本完成自动/人工验收。
7. 生成新的完整部署 ZIP 和单文件升级 BAT。
8. 新建对应版本归档目录；不得修改 V1.0.0 归档。
9. 只把客户需要的文件发给客户，并提供一句话升级说明和 SmartScreen 说明。
