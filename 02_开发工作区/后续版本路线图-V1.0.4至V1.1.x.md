# 会议室预约系统后续版本路线图（V1.0.4～V1.1.x）

> 制定日期：2026-07-28
>
> 当前基线：V1.0.3 Windows 实机验收候选
>
> 文档性质：产品与工程规划基线，不是发布承诺、正式验收记录或外发说明

## 1. 总体原则

1. V1.0.3 保持已经确认的范围，不追加修改预约、API、大屏、提醒或数据库变更。
2. V1.0.4～V1.0.9 每个版本只设置一个主要用户目标，并只拆分与该目标直接相关的代码。
3. 正常业务路径应尽量自动完成；只有异常情况才要求用户补充填写。
4. 新增一次操作，至少应减少一次人工查找、重复填报、纸面登记或催办。
5. 同一个业务字段不得在系统内重复录入；每个新增必填字段必须有明确使用者和使用场景。
6. 不为了保持旧数据库版本而拒绝必要迁移，也不预建尚未投入使用的表和字段。
7. 每次数据库迁移必须连续、可验证、可回滚，并覆盖旧客户数据和重复运行。
8. 主数据库是唯一权威业务数据源。API、大屏和提醒只能通过固定、最小化的数据接口访问，
   不得直接读取 SQLite、执行任意查询或绕过业务权限。
9. 客户业务数据继续留在单位局域网；任何云端、互联网或第三方数据处理都不在本路线图范围。
10. 自动化通过不等于普通用户 Windows/UAC/SmartScreen/EDR/局域网实机验收通过。

## 2. 版本依赖关系

```text
V1.0.3 界面与正式更新通道候选
   │
   ├─ V1.0.4 修改预约
   ├─ V1.0.5 变更可追溯
   ├─ V1.0.6 安全只读 API
   ├─ V1.0.7 局域网大屏
   ├─ V1.0.8 网页内提醒
   ├─ V1.0.9 长期维护基线
   │
   ├─ V1.1.0 工伤笔录履约协同工作台
   └─ V1.1.1 Windows 原生提醒助手候选
```

版本顺序可以在正式立项时调整，但依赖不得倒置：大屏先使用固定只读 API，提醒先验证服务端
规则和网页体验，Windows 客户端建立在稳定 API、身份和提醒规则之上。

## 2.1 升级兼容测试效率治理（V1.0.4 开工前建立）

### 目标与边界

- 不通过删除兼容场景、降低数据校验或跳过候选版全量矩阵来换取速度。
- 将兼容对象从不断增长的“历史版本号”改为数量相对稳定的“安装状态族”。
- 将历史兼容收敛与本期目标升级分开验证，避免每个新版本与所有旧版本重新组成笛卡尔积。
- 这项工作只调整测试夹具、测试驱动和 CI 编排，不改变产品功能、数据库、依赖、
  Windows runtime 或普通用户的一键更新入口。
- 普通用户仍只需运行一个完整更新包；测试内部拆成多阶段不得转化为用户手工串行安装多个包。

### 统一收敛模型

后续正式更新通道统一采用两段式内部模型：

```text
受支持的历史安装状态
        │
        ├─ 干净旧版本
        ├─ 修复完成/未完成状态
        ├─ 旧累计升级残留
        └─ 特殊路径和可恢复故障状态
        │
        ▼
经过逐文件与数据校验的可信兼容基线
        │
        ▼
当前候选目标版本
```

- “历史状态 → 可信兼容基线”形成可冻结、可重复使用的兼容桥。
- “可信兼容基线 → 当前目标版本”是每个新版本主要新增的升级路径。
- 历史兼容桥与本期更新器分别加载、分别校验，任何一段失败都不得继续提交目标版本。
- 数据库迁移仍必须在副本上运行并严格检查；兼容桥不得伪造数据库版本或掩盖损坏状态。
- V1.0.9 形成长期维护基线后，历史兼容桥冻结为独立受审计资产；后续只追加必要的
  “维护基线 → 新版本”路径。

### 安装状态族

升级测试至少按以下状态族管理，不再把每个补丁版本机械复制成一套测试：

1. 最老受支持的干净安装：包括缺少版本文件或旧数据库标记的真实历史形态。
2. 上一正式版本的干净安装。
3. 已完成修复但尚未进入新正式通道的安装。
4. 修复或正式更新的未完成事务状态。
5. 旧累计升级状态、锁、回滚目录和故障 BAT 残留。
6. 重复运行、并发锁、提交边界中断和目标健康检查失败。
7. 中文、空格、括号、`&`、非系统盘等特殊安装路径。
8. 损坏状态文件、跨安装状态、负载哈希不一致等必须拒绝的安全状态。
9. 空数据、典型合成数据和包含未知客户文件的数据保留状态。

每个状态族使用不含真实客户信息、密码或密钥的合成夹具，并由声明式清单记录：

- 夹具身份和来源版本；
- 版本文件、数据库标记、事务阶段和残留类型；
- 适用的 `fast`、`windows`、`nightly`、`candidate` 标签；
- 期望成功、期望拒绝或期望回滚；
- 目标程序版本以及必须保持不变的数据树。

测试驱动从清单生成场景，避免在 PowerShell 和 Python 文件中重复手工拼装安装状态。
只有业务意义或安全边界不同的状态才增加新夹具；等价状态采用代表性用例或成对组合，
不做所有维度的无意义全排列。

### 分级测试门禁

1. **提交级快速检查**
   - 应用、迁移、打包器、状态清单和事务引擎单元测试。
   - 不启动真实 BAT，不重复构建相同候选包。
   - 目标耗时：不含排队不超过 3 分钟。
2. **PR 风险相关检查**
   - 文档改动只做文档和静态契约检查。
   - UI/模板改动运行应用测试、包内容契约和一次正式更新冒烟。
   - 数据库、更新器、runtime、BAT、PowerShell 或工作流改动运行对应 Windows 矩阵。
   - 目标耗时：相关 Windows 检查不含排队不超过 6 分钟。
3. **main 与夜间全量检查**
   - main 至少运行全部正式支持状态；夜间增加拒绝路径、故障注入和旧历史状态。
   - 旧历史状态即使不在每次 PR 中运行，也不得从候选发布矩阵中删除。
4. **候选发布检查**
   - 完整运行受支持旧状态、上一正式版本、重复运行、回滚、中断恢复、特殊路径和
     data/密钥/地址状态保留。
   - 目标耗时：不含排队不超过 12 分钟；不得因超时预算自动降低覆盖。
   - 全绿后仍只代表自动化通过，普通用户 Windows/UAC/SmartScreen/EDR/局域网验收
     继续作为独立门禁。

### CI 并行与构建复用

Windows 工作流逐步拆成以下并行任务：

- `app-and-package-unit`：应用、迁移、打包和静态契约；
- `legacy-bat-integration`：旧 BAT 与历史兼容桥；
- `formal-clean-upgrades`：干净旧版本和上一正式版本；
- `recovery-and-rollback`：未完成事务、重复运行、并发、失败回滚和拒绝路径。

同一提交的候选包只构建一次，其他任务下载同一 Actions 工件并重新校验 SHA-256、
文件清单和 runtime 树哈希。冻结 runtime、历史安装夹具和兼容桥可以按内容哈希缓存，
但缓存命中不能代替重新验签或树哈希验证。PR 更新时取消同分支已经过时的运行，避免旧
提交继续占用 Windows runner。

### 故障注入规则

- Python 单元测试优先通过 `fault_hook` 或测试驱动在明确事务阶段中断。
- Windows 集成优先由独立测试驱动终止未篡改包的进程或构造经过严格校验的合成状态。
- 为测试失败而篡改的包和状态不得继续冒充正式发布包或真实历史残留。
- 仍保留少量真实零参数 BAT 端到端失败测试，用于验证退出码、日志、回滚和用户提示。
- 测试辅助开关不得在普通用户入口中形成绕过签名、权限、哈希或数据库检查的后门。

### 分阶段落地

- **V1.0.4 开工前**：建立声明式状态清单、`fast/full` 标签、候选包单次构建复用、
  CI 并行骨架和过期运行取消；不改变 V1.0.4 用户功能范围。
- **V1.0.5**：预约测试按领域拆分，同时把升级状态生成、断言和 Windows 驱动拆成
  可复用模块；开始记录各任务耗时和最慢场景。
- **V1.0.9**：冻结历史兼容桥和长期维护基线；当前版本与前两个正式版本在相关 PR
  中运行，更老的受支持状态在夜间和候选阶段全量运行。

## 3. V1.0.4：修改预约

### 用户目标

- 预约人可以修改本人尚未开始、未取消的预约。
- 管理员可以在权限范围内协助修改。
- 房间、日期、开始时间和结束时间修改后重新执行完整冲突检查。
- 已开始、已结束和已取消预约不得被普通用户修改。
- 修改成功后仍保持同一预约身份，不通过“取消后重新新建”伪装修改。

### 工程目标

- 抽离预约创建、修改、取消共用的校验、权限、冲突检查和事务逻辑。
- 预约与 `reservation_slots` 的变更必须在同一数据库事务内完成。
- 保留顶层 `app.py` 兼容入口，不进行一次性全项目重写。

### 明确不做

- 不做审批流、改期申请、批量改期或周期预约。
- 不把修改通知扩展到短信、微信、邮件或互联网服务。

## 4. V1.0.5：预约变更可追溯

### 用户目标

- 预约详情显示最后修改时间和“已修改”标识。
- 用户和管理员能查看必要的预约变更记录。
- 记录操作者、操作时间、变更类型和必要的新旧值。

### 工程目标

- 建立追加式预约事件记录；业务表当前值和事件记录职责分离。
- 抽离预约查询仓储、业务服务和权限策略。
- 将预约测试从单体测试文件中按领域拆分。
- 将升级状态生成、公共断言和 Windows 集成驱动拆成可复用模块。

### 明确不做

- 不做复杂审批、电子签章或以日志代替正式业务文书。
- 不在大屏、通知或普通日历中公开变更明细。

## 5. V1.0.6：安全只读 API

### 用户目标

- 为后续大屏和受控本地工具提供稳定、版本化的只读接口。
- 第一批接口只提供房间、时间、占用状态、系统健康等必要信息。

### 工程目标

- 建立 `/api/v1` 独立 Blueprint、统一错误格式、字段序列化和只读鉴权。
- 使用服务端字段白名单；接口不得返回备注、密码、密钥或未批准的个人信息。
- API 客户端不得直接接触 SQLite 文件或提交任意 SQL。
- 为令牌生成、撤销、轮换、权限范围和访问日志预留明确边界。

### 明确不做

- 不提供互联网公开 API。
- 不提供预约写入、任意筛选、全库导出或第三方云端连接。

## 6. V1.0.7：局域网大屏

### 用户目标

- 提供适合电视、横屏显示器和普通浏览器的当天房间状态页面。
- 显示当前时间、房间是否占用、当前时段、下一时段和最后更新时间。
- 网络中断时保留最后一次结果，并明确显示连接异常。

### 隐私边界

- 默认不显示预约人、当事人、单位、案号和备注。
- 如确需候场标识，使用单位批准的匿名号码或最小化称谓。

### 工程目标

- 大屏只消费 V1.0.6 的公开只读接口，不导入应用内部数据库模块。
- 按功能拆分 `calendar`、`reservation-form`、`reservation-dialog` 和 `display` 前端脚本。
- 不引入前端框架、构建链或新运行时依赖。

### 明确不做

- 不做统计图表、排行榜、月度分析、广告轮播或多网点管理。

## 7. V1.0.8：网页内预约提醒

### 用户目标

- 登录用户保持系统页面打开时，在预约时间到达后看到本人提醒。
- 点击提醒可进入预约详情；用户主动开启后可以播放声音。
- 修改或取消预约后旧提醒自动失效，同一提醒不得重复轰炸。

### 工程目标

- 建立独立提醒查询、到期判断、防重复投递和确认逻辑。
- 提醒接口只允许读取当前用户的必要字段。
- 断网恢复或电脑唤醒后只在受控宽限窗口内补发，不补发大量历史提醒。

### 明确不做

- 不承诺浏览器关闭、电脑休眠或标签页冻结后仍能提醒。
- 不使用云推送、短信、微信或第三方通知服务。
- Windows 原生通知留到独立客户端版本。

## 8. V1.0.9：长期维护基线

### 用户目标

- 管理员可以查看脱敏的系统状态：程序版本、数据库版本、局域网地址、最近备份、
  API/大屏连接和基础运行健康。
- 可以导出不含密码、密钥和预约内容的诊断信息，便于维护人员定位问题。

### 工程目标

- 将网络地址、安装身份、单实例、健康检查和启动逻辑从单体文件拆到 `runtime` 模块。
- 将应用工厂、数据库、认证、预约、管理员、API、提醒拆为清晰模块。
- 将单体测试文件按认证、预约、管理员、网络、API、提醒和迁移拆分。
- `app.py` 保留为兼容应用入口，`server.py` 收敛为启动编排；不进行框架重写。
- 更新正式更新包的受管文件清单、删除旧受管文件规则和跨版本回归矩阵。
- 冻结历史兼容桥，建立“当前及前两个正式版本按风险运行、更老状态夜间和候选全量运行”
  的长期支持策略。

### 明确不做

- 不借结构整理增加新业务流程。
- 不同时更换数据库、Web 框架、依赖和 Windows runtime。

## 9. V1.1.0：工伤笔录履约协同工作台

### 产品定义

V1.1.0 不再只定义为“会议室预约系统”，而定义为：

> 部署在单位局域网内，围绕工伤笔录任务，把预约、准备、到场、执行、完成和必要后续
> 提醒串联起来的轻量协同工作台。

正式名称建议为“工伤笔录预约与协同工作台”，页面短名称建议为“工伤笔录工作台”。
它不替代正式工伤认定业务系统，不自动产生受理、认定或送达等法律程序结论。

### 核心变化

- 当前核心对象是“一条预约”；V1.1.0 核心对象变成“一项笔录任务”。
- 预约继续负责房间和时间冲突；任务负责到场、执行和必要后续。
- 首页从单纯日历升级为“今日笔录工作台”，日历继续作为资源调度视图。

### 首期闭环

- 当前与即将开始的笔录任务自动来自预约，不要求重复建台账。
- 一次点击登记“已到场”“进行中”“已完成”或“爽约”。
- 时间、房间、预约人、当事人/单位和案号从已有预约继承。
- 正常完成不要求填写额外说明；只有爽约、需要再次笔录或材料缺项等异常才补充。
- 可登记最小化的材料状态和缺项名称，但不保存身份证、病历、医疗影像或音视频原件。
- 必要的后续日期和提醒与当前经办人关联。
- 操作记录由系统自动生成，不要求用户为了留痕重复录入。

### 用户负担验收门槛

- 新建预约耗时不得明显高于当前版本。
- 正常完成一场笔录，新增操作不得超过两次点击。
- 同一字段不得在预约、任务和台账中重复填写。
- 必须替代至少一项现有 Excel、纸面登记或人工催办。
- 先由 3～5 名真实工作人员试用至少两周，再决定是否扩大使用。
- 试用应记录预约耗时、额外点击、漏办/爽约、重复录入和自愿持续使用情况。

### 安全门槛

- 先完成数据清单、用途、可见范围、保存期限和删除/归档规则。
- 权限从“普通用户/管理员”扩展为按职责和经办范围最小授权。
- 大屏和 Windows 通知不得显示当事人、案号、备注或材料内容。
- 局域网传输、服务器磁盘、备份、密钥和恢复流程应形成独立安全方案。
- 登录、查看敏感详情、修改、导出和权限调整必须可审计。
- 上线前由使用单位的信息化、网信、保密或安全责任部门确认定级、测评和密码应用要求。

### 明确不做

- 不处理正式工伤认定结论，不自动判断是否属于工伤。
- 不建立身份证、病历、医疗资料、笔录全文、音频或视频档案库。
- 不建设群众互联网门户、云同步、多地区协同或 AI 自动生成正式文书。
- 不把预约成功自动解释为已经申报、受理、调查、决定或送达。

## 10. V1.1.1：Windows 原生提醒助手候选

### 用户目标

- 浏览器关闭后，安装了提醒助手并已登录/配对的 Windows 用户仍可收到本人预约提醒。
- 通知只显示房间、时间和通用提示；点击后打开系统并重新验证登录状态。

### 工程与安全目标

- 使用独立、最小权限、可撤销的用户令牌，不在电脑上保存管理员账号密码。
- 客户端只读取本人提醒，不直接读取数据库。
- 支持断网、睡眠唤醒、修改/取消失效、多设备防重复和令牌撤销。
- 明确客户端版本、升级、开机启动、日志和卸载边界。

### 发布边界

- 该版本增加独立 Windows 客户端，必须单独完成普通用户安装、通知权限、开机启动、
  SmartScreen、杀毒软件/EDR、单位软件白名单和锁屏隐私验收。
- GitHub Windows runner 只能验证代码和安装流程，不能替代上述实机验收。

## 11. 每个版本的完成定义

每个候选版本至少满足：

1. 需求范围、明确不做和数据库版本写入候选开发记录。
2. 应用测试、迁移测试、升级包工具测试和候选包反向校验通过。
3. 覆盖上一正式版本直升、受支持旧版本累计升级、重复运行、失败回滚和中断恢复。
4. 验证 `data` 全树、账号、预约、密钥、安装身份、局域网地址状态、备份和日志保留。
5. 完成与改动风险相称的冷审和安全检查。
6. GitHub Actions 全绿。
7. 只生成候选版；普通用户 Windows 10/11 和真实局域网验收完成前，不形成正式发布结论。
